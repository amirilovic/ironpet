# ironpet v1 spec

A personal macOS desktop pet that floats above all windows, watches coding agents, and runs agent tasks for me.

## Decisions

| Area | Decision |
| --- | --- |
| Audience | Just me. Rough edges are fine. |
| Platform | macOS only, native Swift (AppKit + SwiftUI), Dock app. |
| v1 jobs | Agent watcher, quick chat, screen-aware help. |
| Later | One window with a sidebar (chat, agents, alerts, tasks, automations, transcripts), focus coach, calendar, dev signals, more chat backends, auto-hide. |
| Movement | Stays where dragged (position persists). Idle animations, eyes follow cursor. |
| Art | Ghost, a chibi white direwolf in a Night's Watch cloak, drawn in code by `tools/make_pet.swift` (alternates: Mochi, a mint wolf, and a hamster, panda, bunny and cat on the same body and poses) into the Codex v2 atlas layout (1536x2288, 8x11 cells of 192x208). |
| Success | I stop alt-tabbing to check agents, fire small tasks from the pet, use screenshot help daily. |

## Agent watcher

- Watches Cursor (IDE chats and CLI) and Claude Code via global hooks that the pet installs itself.
  - Merges into each watched agent's own config, preserving other entries (Superset, Orca): `~/.cursor/hooks.json`, `~/.claude/settings.json`, `~/.codex/hooks.json`, `~/.gemini/settings.json`. GitHub Copilot gets its own file in `~/.copilot/hooks/` and Pi gets an extension in `~/.pi/agent/extensions/` that calls the same hook script. `SessionStore` maps each agent's events (Codex uses Claude's names; Gemini's are BeforeAgent/AfterAgent/BeforeTool; Copilot's are camelCase; Pi's come from the extension). The agents offered are the ones found on this Mac.
  - Backs up each file once to `<file>.ironpet-backup` before the first write. Uninstall removes only ironpet entries.
- Hooks POST to the pet on `127.0.0.1` with a token from `~/.ironpet/token`. The hook never blocks or fails the agent (1s timeout, always exits 0).
- Status per session: `running`, `needsInput`, `done`, `failed`, `idle`.
- Pet shows one mood by priority `needsInput > failed > done > running` with a count badge. Click opens the session list.
- `done` and `failed` stay until acknowledged (clicked, jumped to, or a new prompt starts).
- Speech bubble (and optionally a macOS notification) on entering `needsInput`, `failed`, `done`.
- Jump to source: iTerm tab when the hook saw `ITERM_SESSION_ID`, otherwise the Cursor window for the workspace (`open -a Cursor <root>`). Exact Cursor chat/terminal tab is out of scope.

### Event mapping

| Source | Event | Effect |
| --- | --- | --- |
| Cursor | `sessionStart`, `beforeSubmitPrompt`, `postToolUse`, `afterAgentResponse` | running (headless CLI never fires `beforeSubmitPrompt`) |
| Cursor | `stop` (`status`: completed / error / aborted) | done / failed / idle |
| Cursor | `sessionEnd` | remove unless unacknowledged done/failed |
| Claude Code | `UserPromptSubmit`, `PreToolUse`, `PostToolUse` | running |
| Claude Code | `Notification` (`permission_prompt`) | needsInput |
| Claude Code | `Stop` | done |
| Claude Code | `SessionEnd` | remove unless unacknowledged done/failed |

Cursor also runs Claude Code hooks from `~/.claude/settings.json` ("Third-Party Imports", on by default, always on in cursor-agent), so each Cursor event would arrive twice, the second time labelled Claude Code and often without a folder. The hook script exits early for `claude` when `CURSOR_VERSION` is set (only Cursor sets it for hooks), and the app drops `claude` events whose payload has `cursor_version`.

Known gap: Cursor has no hook for "waiting on the user's approval", so Cursor sessions never show `needsInput`.

## Quick chat (milestone 2)

- ⌥⌘G (or clicking the pet when no watched agent needs attention) opens a focused chat bubble. Opening the bubble activates ironpet (and closing it reactivates the previous app), because Wispr Flow (hold fn) finds the focused text field through the frontmost app's Accessibility tree. A dictation shows up as one large insert; with "Send automatically after dictation" on, it sends after 0.8s.
- Agents over ACP (`Chat/ACP/`): `ACPClient` speaks newline-delimited JSON-RPC, `ACPBackend` keeps one process per chat and maps `session/update` onto the chat's events. The agent comes from the catalog in `AgentCatalogData.swift` (generated from the ACP registry) and is chosen in the chat settings. Claude Code, Codex and Pi run through the `.mjs` adapters in `Contents/Resources/acp/` on the user's Node 22+ (or a Bun downloaded on request into `~/.ironpet/runtime`), pointed at the user's own CLI by `CLAUDE_CODE_EXECUTABLE`, `CODEX_PATH` or `PI_ACP_PI_COMMAND`. Executables are found on the login-shell PATH. Model choice is stored per agent; threads store the agent id, ACP session id and folder.
- Working directory: frontmost Cursor window (window title matched against `windowsState.openedWindows` in Cursor's `storage.json`) or iTerm session path (AppleScript `session.path`). The chat never switches folder or session by itself, so the detected folder is not applied. Only the user changes them (New Chat, the folder picker, a saved thread, the agent switch). With no folder chosen yet, a "Which project?" picker (recent folders, "No project" → `~/.ironpet/scratch`, or choose a folder) shows and nothing sends until one is picked.
- Approvals: the agent sends `session/request_permission` with the tool call (`kind`, `title`, `rawInput`) and a list of options. `ApprovalRules` decides whether ironpet answers at once (read, search, think, fetch, read-only MCP verbs, memory-file edits, and everything non-destructive in Auto mode) or shows a card. The reply picks `allow_once` or `reject_once`. Identical repeated requests within a turn share one card. ironpet cannot make an agent ask; an agent that does not send the request runs its tools unprompted.
- Auto mode: per-chat toggle handled in ironpet. The agent stays in its asking mode, ironpet auto-allows, and destructive commands (`rm -rf`, `git reset --hard`, `git push --force`, dropping tables) still require approval.
- Stop sends `session/cancel` and keeps the process. Threads are kept and reopened with `session/load`; the replayed transcript is ignored because the chat already holds it.
- ACP chat runs set `IRONPET_ACP_RUN=1`; the hook script skips them so they do not show up as external sessions.
- Memory: the agent writes editable markdown in `~/.ironpet/memory/` (`me.md` plus one file per project), injected into each chat.

## Screen-aware help (milestone 3)

- ⇧⌥⌘G captures the frontmost window, ⌃⌥⌘G a dragged region (also in the pet's right-click menu). Opens quick chat with the image attached.
- Screenshots go to `~/.ironpet/screenshots/` (last 30 kept), which is passed as `additionalDirectories` where the agent supports it. Images go as ACP image blocks when the agent advertises `promptCapabilities.image`; otherwise the prompt names the file.
- The app is signed with a local self-signed identity (`scripts/make_signing_identity.sh`, run by `install.sh` when missing) so TCC permissions survive rebuilds. `scripts/uninstall.sh` removes hooks and the login item by running the installed binary with `--uninstall` (which reuses `HookInstaller`), then deletes the app, Keychain item and preferences, and asks before deleting `~/.ironpet` and the identity.
- Needs Screen Recording permission (also unlocks Cursor window titles for workspace detection). No app exclusions.

## Pet states

| ironpet state | Atlas row |
| --- | --- |
| idle | 0 idle, plus look rows 9-10 following the cursor |
| working | 7 running |
| needs input | 6 waiting |
| done | 4 jumping once, then 8 review |
| failed | 5 failed |
| listening | 3 waving once, then idle |
| dragged | 1 / 2 running right / left |
| sleeping | idle frame 0, dimmed (no row exists); after 10 min with no activity |
| drinking (water reminder) | 11 sipping from a glass, ironpet extra row |
| stretching (stretch reminder) | 12 arms overhead, side stretch, ironpet extra row |

Rows 11-12 are ironpet additions below the Codex v2 layout, so ironpet's sheet is 1536x2704. Atlases without them (Codex pets, older sheets) play the waving row instead.

Reduced motion: frame 0 only. Pet art is loaded from `pet.sprite` in config.json, else `~/.ironpet/pet/spritesheet.{webp,png}`, else the Ghost sheet bundled in the app (generated by `scripts/bundle.sh` with `tools/make_pet.swift`), else a drawn placeholder.

Pet gallery (`App/PetGallery.swift`, `Pet/PetLibrary.swift`): Settings → Pet lists the six sheets `scripts/bundle.sh` generates into `Resources/pets/`, every valid PNG or WebP in `~/.ironpet/pets/` (same name replaces the bundled pet), and a `pet.sprite` that points elsewhere. Invalid files are skipped. Each tile plays idle, waving, jumping and running with the pet's own `AtlasRow` durations. One 15 Hz timer drives all tiles and a 2 s poll of the folder (names, sizes, dates) reloads it; both run only while the gallery is on screen in a visible Settings window. Reduce Motion shows idle frame 0 and starts no animation timer. Selecting a tile sets `pet.sprite` and renames the pet only if its name is a built-in pet's name or the previous pet's name. "Add from file…" copies a validated sheet into the folder. "Build a new pet" sends `/ironpet-pets <description>` (`PetPrompt`), installing the skill first through `SkillManager` when no agent has it. The skill holds the atlas layout and finds the generator itself, and a test keeps it in step with `AtlasRow`. `skills/ironpet-pets/SKILL.md` is compiled into `BundledSkillsData` like every skill, so Settings → Skills lists it and auto-update keeps installed copies current, opens the chat without calling `prepareForShow`, so the session and folder stay as they are, and sends it in the current thread. `/test/build-pet` triggers it in test mode. OpenAI's built-in pet art is never used or bundled.

Status of milestone 2: built. Threads are saved to `~/.ironpet/threads/` and reopened from the history menu (reopened with `session/load`). Memory files are created on first use, injected into the first turn of each thread, reachable via `--add-dir`, and edits to them never need approval.

## Additions after v1

- **Agent summaries.** Per turn, the watcher records edited files (Cursor `postToolUse`, Claude `PostToolUse` on edit tools) and the final reply (Cursor `afterAgentResponse.text`; Claude `Stop.last_assistant_message` or the tail of `transcript_path`). The summary is "Edited N files · first sentence of the reply" and is used in done/failed notifications and the session list. Headless cursor-agent sends no reply event, so its summary is files only.
- **Approve from notifications.** Approval notifications (chat hidden) use a category with Allow / Deny actions that call the same `decide` as the chat card; resolving a card clears its notification.
- **Alerts (`Signals/`).** An alert is a `Signal` in `SignalStore`: an id, label, title, subtitle, optional URL, symbol, mood and an optional "Ask Ghost" prompt. Script automations create them with `alert` actions. A new or changed alert gets a bubble (the first script run adds alerts quietly), and the list keeps it until it is dismissed or the script resolves it. The most urgent mood among open alerts sets Ghost's mood and badge. The GitHub and Sentry alerts are script automations (`github-alerts`, `sentry-alerts`, templates in `Automations/AutomationDefaults.swift`), not built-in code, and are not created on a fresh install. The GitHub script runs one `gh api graphql` query per host in `~/.config/gh/hosts.yml` every 2 min (own open PRs with CI rollup and review decision, plus review requests) and keeps each PR's CI and review state in its script state. It alerts on failing CI, changes requested and review requests, resolves them when they clear, and shows a short bubble for CI passed and approved. The Sentry script reads `~/.ironpet/sentry.json` and the Keychain token, queries `is:unresolved firstSeen:-1h` and `is:unresolved is:escalating` with curl, alerts on each issue, and resolves an escalation when it stops. Each alert offers Open, Ask Ghost (prefilled prompt, not auto-sent) and Dismiss.

- **MCP in chat.** Headless cursor-agent loads the user's MCP servers (signed in with `cursor-agent mcp login`). Cursor fires `preToolUse` (`MCP:<tool>`, allowed) and then `beforeMCPExecution` (tool, input, server URL), which ironpet gates; Claude Code tools named `mcp__<server>__<tool>` are gated on `PreToolUse`. Read-only verbs (`get`, `list`, `search`, `find`, `fetch`, `read`, `describe`, `whoami`, `lookup`, `show`, `count`) pass; everything else asks, and in Auto mode still asks if the arguments match the destructive pattern. Sentry: REST API for alert polling, Sentry MCP for "Ask Ghost" investigations.
- **Shared MCP sign-ins (opt-in, `integrations.shareMCPSignIns` in `~/.ironpet/config.json`).** cursor-agent keeps OAuth sign-ins per workspace in `~/.cursor/projects/<slug>/mcp-auth.json` (slug = path with non-alphanumerics as `-`). Before each pet chat run, `MCPAuthSharing` copies every server entry that has tokens (with its client registration) from the most recently modified file into the run's workspace file(s), covering both `/tmp/...` and `/private/tmp/...` slugs. This relies on an internal Cursor file format.
- **Automations (`Automations/`).** Reminders, watchers and scheduled jobs are `Automation` records in `~/.ironpet/automations.json` (trigger `interval`, `daily`, `once`, `poll` or `script`; action `bubble`, `prompt` or `shell`, none for a script). `AutomationStore` loads and validates the file (unknown keys, bad times, literal secrets and duplicate ids are errors), polls its modification date every 2 s, keeps the last good list when an edit is invalid and shows a bubble naming the problem, and writes `automations.schema.json` beside it. On the first launch without the file, `AutomationMigration` turns `config.json` reminders into three `active` interval automations (water 45, stretch 60, eyes 20, keeping their enabled flags) and, only when they were already on (`integrations.githubAlerts`, or a `sentry.json` present), the GitHub and Sentry alerts into script automations. A fresh install gets the three reminders only, and the welcome window's GitHub tick adds the GitHub automation. A file from an earlier build with `builtin` sources is rewritten to those scripts on load. `AutomationEngine` takes time and idle state through an `Environment`, so tests drive it with a fake clock. Every 30 s `tick()` adds the elapsed keyboard time to each enabled `active` interval unless the system idle time or the gap since the last tick is `idleResetMinutes` (5) or more, which resets them. One is due at its interval, or at 75% of it while a watched agent or Ghost chat is running, and everything at 75% or more goes out in one bubble. Nothing active goes out while the chat is open, an approval is pending or a session needs input. `wall` intervals, `daily` slots (including missed ones after sleep, once) and `once` ignore keyboard time and busy state. Done jumps Ghost and Snooze makes the automation due again after `snoozeMinutes`. `reminders.paused` holds all time-based automations; polls keep running.
- **Polls (`Automations/PollEngine.swift`).** A port of the necessary parts of agent-trigger's poll engine: run a shell command or `curl` with a timeout (default 30 s) and a 256 KiB output cap, read items with JMESPath (`items`, `id` and `version` expressions, run in-process by the jmespath.swift package, pinned to 1.0.3 because later versions need Swift 6.2 and CI builds with 6.1; filters such as `[?state=='open']` replace agent-trigger's `where`, and regular expressions are not available), and keep a seen set per automation. The first successful run baselines silently; later runs fire for new ids or a changed `version`. Failed runs never baseline. `cooldownMinutes` drops items that arrive too soon after a fire (recorded as `skipped`). Built-in `github` and `sentry` sources call `GitHubWatcher.poll()` and `SentryWatcher.poll()` on the automation's schedule and report through the alerts list. ironpet does not run, call or read agent-trigger.
- **Database (`Support/Database.swift`).** `~/.ironpet/ironpet.db` is ironpet's common database, on the system `SQLite3` module in WAL mode, opened once by `Database` and passed to the features that use it. It knows no feature. Features contribute ordered `Database.Migration`s (a version number, a name, SQL or a closure); the app passes the combined list to `Database.open`. The runner applies the migrations above `PRAGMA user_version`, each in its own `BEGIN IMMEDIATE` transaction that also stores the new version, so a failing one rolls back and leaves the file at the earlier version. A file from a newer ironpet, or one that fails to migrate, is not touched: the app logs it and runs on an in-memory database. All writes run on one serial queue, each in a transaction. Reads use a second read-only connection on a concurrent queue. Other state stays where it was: `config.json`, `automations.json`, threads and meetings are not in the database.
- **Usage (`Usage/UsageStore.swift`, `App/UsageSettings.swift`).** Migration 100 adds `usage_events`: one row per agent turn or transcription request that ironpet runs itself (chat including Telegram, automation prompts, meeting summaries, voice and meeting transcription), with time, feature, model, and only the numbers the agent or provider reported. Missing numbers stay null and show as a dash. Turn cost is the change in the session's cumulative `usage_update` cost since the last record. Agents ironpet only launches or watches record nothing. Rows older than 400 days are deleted at launch and at most once a day after that. Writes go through a background queue. The Usage tab in Settings shows 7, 30 or 90 days by feature and model.
- **Automation state (`Automations/AutomationState.swift`).** The first client of the database, with prefixed tables from migration 1: `automation_seen` and `automation_state` (seen sets and poll state), `automation_runs` (the last 20 per automation), `automation_approvals` (SHA-256 of the approved or rejected command or prompt) and `automation_snoozes` (restored on launch). Seen items unseen for 7 days and runs older than 30 days are pruned at launch and on every write, and state of deleted automations is dropped. Definitions never go in the database. Migration 4 adds `automation_logs` (time, duration, outcome, summary, and up to 8 KiB of detail per run), written for every poll and script run and for every service event (reminder fired, shell, prompt). Lines older than `automations.logRetentionDays` (config.json, 14 by default, 1 to 365) are deleted at launch and at most once an hour after that, and each automation keeps at most 2000. `AutomationLogWindow` shows them, filtered by automation or problems only, refreshing every 3 s.
- **Scripts (`Automations/AutomationScript.swift`).** A `script` trigger runs `poll(state)` in QuickJS (zqqf16/QuickJS-Swift, which vendors the official QuickJS), in the main process, on a background queue. A script automation has no `action` (stored as type `none`, left out of the file). The runtime is created with `enableStdModules: false`, so there is no `std`, `os`, file loader or worker, and no `fetch`, timers or `require`. The prelude module gives the script `sh(command, options)` and `console.log`, which call `HostIO`. A script that needs the network runs `curl` through `sh`. Limits: 32 MiB of memory (`JS_SetMemoryLimit`), an interrupt handler that stops the script after 60 s, 8 `sh` calls per run with each timeout capped at the time left and output capped at 256 KiB, 64 KiB of script, 256 KiB of state, 20 actions. `poll` must be synchronous. It returns `{state, actions}`. The state goes to `automation_script_state`. Each action has a type of `bubble`, `alert` or `prompt`, and the engine carries it out (`AutomationService.perform`). The script cannot cause a side effect itself, and there is no `shell` action because a script can already call `sh`. A `bubble` is an `AutomationNotice` (same `id` replaces it). An `alert` becomes a `Signal` of kind `automation` in the alerts list, with its own label, symbol and mood from `severity`. A hash of each alert as last shown is in `automation_alerts`: a new or changed alert notifies, one listed again unchanged is left alone even if the user dismissed it, `resolved: true` removes it, and the first run adds alerts quietly. A `prompt` runs through `AutomationPrompt`. A script an agent wrote counts as risky text, so its hash needs approval like a shell command. The validator loads the script once in a sandbox that cannot run commands, and requires a `poll` function.
- **Built-in task review (`AutomationDefaults.reviewTasks`).** Id `review-tasks`, `createdBy: user` (no approval), `interval` 10 min `wall`, `prompt` action `/ironpet-tasks`. `AutomationStore.init(builtIns:)` appends a built-in whose id is missing from the file, for a new and an existing file, and leaves one that is there as the user set it (so a switch-off persists). `AutomationService.handle` skips it with `skipped: no open tasks` when `hasOpenTasks` is false (wired to `TaskStore`: any task not done). It reuses the one-message-per-automation rule of chat prompts. In `ChatSession`, when a turn of this automation ends without error and the last assistant text, trimmed, is `ironpet-tasks: no changes`, the items from the prompt onward are removed before the thread is saved, the "finished your task" attention is not raised, and `AutomationEvent.noChange` makes the history say `no changes`.
- **Actions and approval (`Automations/AutomationService.swift`).** `bubble` shows a bubble (and a macOS notification when asked). `shell` runs `/bin/sh -c` with the login-shell `PATH`, a timeout and capped output, and quotes poll item values it substitutes. `prompt` goes into the user's chat through `ChatSession.submitFromAutomation`: a user message with origin `automation` (a small badge in the transcript) and a header line, `Automation "name" (every 5 min):`, in the chat's thread, folder, agent and model, with full tools and MCP servers. It queues behind a running turn like any typed message, and leaves the draft and attachments alone. Without a folder it uses the no-project folder. Each automation has at most one message queued or running in the chat, so a tick that finds the previous one still there is skipped and logged as `skipped: previous run still in the chat`. The history records `sent to chat`, `running in the chat` and the outcome (`finished` or `failed`), never the answer. `agent` and `model` are ignored. A prompt that uses `{{item.*}}`, and a `prompt` action of a script, keep the old path, `AutomationPrompt`: its own `ACPBackend` process in `~/.ironpet/automations/workspace`, restricted, read-only tool calls only. Poll items hold text from outside (an issue title, a web page), and untrusted text must not reach a session that has full tools. An automation whose `createdBy` is not `user` and that has a `shell` action, a `shell` poll source or a `prompt` action waits for Approve in a bubble before its first run. The approval stores a SHA-256 of the command or prompt in `ironpet.db`, so any change asks again, and Reject turns it off. Settings edits count as the user. A run that comes due while unapproved is kept and runs when approved. The last 20 runs of each automation are kept as history.
- **Agents and automations (`Automations/AutomationAgentPrompts.swift`, `AppDelegate.sendToChat`).** `AutomationService.log` calls `considerFix` for every `failed` line. With `automations.autoFix` on (the default), it asks once per failing stretch (an automation that logged `ok`, `baseline` or `fired` ends the stretch), at most every 6 hours per automation (the time of the last request is in UserDefaults, so a restart does not repeat it), and skips paused automations and ones that still need approval. `sendToChat` sends in the current chat and folder, and sends the message without showing the chat, then shows a bubble with Open chat. If a turn is running or an approval is pending, it shows a bubble with Send instead of replacing the chat. The failed run's error goes in the message in a fenced block marked as data. Settings' **New automation…** box sends the user's text the same way, with the chat shown. The messages name the automation tools and, as a fallback, the command line.
- **Skills (`Skills/`, `skills/`).** A skill is a folder `skills/<name>/SKILL.md`. `scripts/gen_skills.py` compiles every one into `Skills/BundledSkillsData.swift`, and a test fails when a folder is not bundled or its text differs. `BundledSkill` has the name, text, a SHA-256 of the text, and the frontmatter description. `SkillInstaller` installs one skill as the real copy in `~/.agents/skills/<name>`, and for each agent whose config folder exists (the parent of its global skills folder, from a table in `SkillInstaller`) a relative symlink in that agent's skills folder. Agents that read `~/.agents/skills` (Codex, Cline, Pi, Warp, Zed, ...) need no link. `--copy` writes a copy per agent. A folder with that name whose `SKILL.md` is not ours is skipped. Status per skill is current, outdated (text differs from the bundled one), foreign or not installed. `SkillManager` runs the installer over all skills and has `updateInstalled()`, which reinstalls the outdated ones only where they already are and adds nothing new. `SkillPrompt` decides what Ghost asks, 15 s after launch: the skills that are missing or outdated where an agent is on the Mac and whose text hash the user has not dismissed (`skillPromptDismissed` holds the hashes). One bubble lists them, with Install or Update. With `skills.autoUpdate` on (config.json, the default), `updateInstalled()` runs first at launch, then the pending skills (missing or outdated, an agent present, not dismissed) are installed with one bubble saying so instead of asking. Turning the switch on in Settings installs the missing ones at once. The Settings → General → Skills section lists every skill with its buttons and the switch. `IRONPET_SKILLS_HOME` replaces the home folder for tests and trial runs. CLI: `IronPet skills install|status|update|remove|list|agents`. The bundled skills are `ironpet-automations`, `ironpet-pets` and `ironpet-tasks`. `ironpet-tasks` covers what to track, the periodic review run as `/ironpet-tasks`, and the three closing rules. A test checks that it names only `tasks_*` tools the MCP endpoint serves.
- **Agent interface.** `POST /mcp` on the loopback server is a small MCP endpoint (`initialize`, `tools/list`, `tools/call`) with nine `automations_*` tools and the `tasks_*` tools (see Tasks); `POST /automations` is the plain form the CLI uses. Both, and Settings, go through `AutomationService.call` and `AutomationValidator`. `ACPBackend.defaultMCPServers` gives every unrestricted chat session a stdio server entry, `IronPet mcp`, that forwards to `/mcp` using `~/.ironpet/port` and `token`. `IronPet automations …` is the CLI. Test mode adds `/test/automations*` endpoints (advance the clock, stub prompt answers, press bubble buttons).
- **Speech bubbles (`Pet/Bubbles.swift`, `App/Announcer.swift`).** Every announcement (agent needs input / failed / done, chat approvals, alerts, reminders, chat finished) is a bubble in a transparent non-activating panel beside the pet, on the side with more room, tail pointing at his head; it follows him when dragged. Up to 4 stack, newest at the bottom; the same id replaces (one per session, approval, alert). Lifetimes: approvals until answered, reminders 3 min, failed / needs input / alerts 40-45 s, done and passed 15 s, paused while hovered. Bubbles carry the same actions the notifications had (Allow / Deny, Done / Snooze, Open / Ask Ghost) and play the "Pop" sound unless the news is good. Hidden while the chat or agents window is open. macOS notifications are off by default; right-click → "Also show macOS notifications" (`notifications.system`) sends both.
- **Agents window (`Pet/AgentsPanel.swift`).** A key panel instead of an NSPopover so it is clamped to the pet's screen (NSPopover got cut off with the pet at the right edge). Opens below the pet, or above when there is no room; closes on Esc or losing focus. Tabs: Agents and Alerts.

- **Configuration (`Support/Config.swift`, `App/SettingsWindow.swift`).** `~/.ironpet/config.json` holds pet name and sprite, hotkeys, reminders and integrations. The file is laid over the encoded defaults before decoding, so it only needs changed keys; values are clamped (minutes ≥ 1, empty name → default). An invalid file yields defaults plus an error shown in Settings, and is copied to `config.invalid.json` before Settings overwrites it. `ConfigStore` (main actor) polls the file's modification date every 2 s; `AppDelegate` re-registers hotkeys and reloads the atlas on change, everything else reads the config where it's used. Hotkeys are Carbon `RegisterEventHotKey` from strings like `cmd+opt+g`; a combination another app holds is reported in Settings, and hotkeys are unregistered while the Settings recorder is listening. Chat backend, model, recent folders and window size stay in UserDefaults as UI state.

- **First run (`App/SetupWindow.swift`).** Shown when setup was never finished or skipped and there is no `config.json` (a config brought from another Mac counts as set up). It offers pet name, hooks per agent (pre-ticked when the tool is detected or ironpet's hooks are already there), launch at login, break reminders and GitHub alerts. Start writes `config.json`, installs the chosen hooks, removes unticked ones left by an older version, and switches chat to Claude Code if cursor-agent is missing. Not now or closing the window writes the default config (no hooks). Hooks are recorded as `integrations.cursorHooks` / `claudeHooks`; on each launch the chosen ones are refreshed, and toggling them in Settings installs or removes only that agent's hooks.

## Tasks

The agent's board, not the user's: the agent keeps track of the items, the user tells it what happened. Moving cards by hand would lose what the agent knows, so the UI only marks done, deletes, and adds or skips meeting suggestions.

- **Store (`Tasks/TaskStore.swift`).** Migration 200 adds `task_items` (id, title, notes, status, source, due, created, updated, closed), `task_links` (thread, session, url or file per task, in order), `task_events` (one row per create, status change, edit, note, close and delete, with who did it: `user`, `agent:mcp`, `agent:cli`, `test`) and `task_suggestions`. Statuses are fixed in v1: `backlog`, `in_progress`, `needs_you`, `done`. Ids are slugs of the title (`AutomationValidator.slug`), never reused while a deleted task's history is kept. Done tasks older than `tasks.keepDoneDays` (30, 1 to 365) and history of tasks that no longer exist are pruned at launch and at most daily. `TaskStore.call(op, args, by:)` is the one entry for MCP, the CLI and test endpoints; `TaskValidator` checks titles (1 to 200 characters), notes (4 KiB), statuses, ISO 8601 due dates and links (at most 10, `url` must be http or https).
- **Agent interface.** `Bridge/MCPEndpoint.swift` serves `initialize`, `tools/list` and `tools/call` on `POST /mcp` for both tool sets and routes `automations_*` to `AutomationService.call` and `tasks_*` to `TaskStore.call`. `POST /tasks` is the plain form `IronPet tasks …` uses. `Memory.preamble` tells every chat that it keeps the list, when to add, close and move to needs you, and never to start work on a task unless asked. Automation prompts run in the user's chat and can change tasks like any message there. Restricted sessions (prompts that use `{{item.*}}`, meeting summaries) get no MCP servers, so they cannot. `tasks_list` results say that task text is data, not instructions.
- **Meetings (`Tasks/ActionItems.swift`).** The summary prompt already asks for `- [ ] <task> (owner: …, due: …)` lines under `## Action items`. After `summary.md` is written, `ActionItems.mine` keeps the items whose owner is "Me", `TaskStore.suggest` drops ones that match an existing task or suggestion by title, and a bubble offers Add all and Review. Accepting makes a `backlog` task with source `meeting` and a `file` link to the meeting folder; a due that is not an ISO date stays in the notes. Suggestions are text only and never sent to an agent. `tasks.meetingSuggestions` (on) turns this off.
- **UI (`Pet/TaskListView.swift`).** A Tasks tab in the agents panel between Alerts and Actions, counting needs you, in progress and suggestions. Sections: Suggestions, Needs you, In progress, Backlog, Done (last 7 days, collapsed). "Tell Ghost…" sends its text through `AppDelegate.sendToChat`.

## Telegram

Opt-in (`telegram.enabled`, off by default). `TelegramBridge` long-polls `getUpdates` (30 s, offset in UserDefaults; a new bot's backlog is skipped) through `TelegramAPI`, which takes the token from the Keychain (`ironpet.telegram`) on every call. Messages from ids in `telegram.allowedUsers` go to `ChatSession.submitFromTelegram`, which adds a user item with `origin: "telegram"` to the current chat and never calls `use` or `newChat`; a busy agent queues it and the queue drains when the turn ends. `ChatSession.onTelegram` reports started, waiting for approval, finished(last assistant text) and failed for turns that began in Telegram, and the bridge sends typing every 4 s and the answer through `TelegramFormat` (Markdown to Telegram HTML, split on converted length, code blocks closed and reopened across parts, plain-text retry on a 400). Pairing: with nobody allowed, a `/start` from a private chat becomes a pending request (max 3) and a bubble. Errors set the status line and back off 2, 4, … 300 s. Uploads: `TelegramMediaStore` picks the largest photo size, documents and videos as files and voice, audio and video notes as voice, refuses over 20 MB before and after `getFile`, and saves under `~/.ironpet/telegram/files/<chat>/<stamp>-<id>/<name>`; messages with a shared `media_group_id` in one poll become one chat message. Incoming work with files runs through one in-order queue so text sent after a download does not overtake it. Voice goes through `TelegramVoice` (AVFoundation to 16 kHz WAV when it can decode, else the raw file with its MIME type) and the Settings → Voice server; the transcript is echoed as `🎙 text` and sent as the message text. Approvals: `ChatSession` emits `approval` and `approvalDecided` for Telegram-started turns, the bridge sends Approve and Reject inline buttons (`a:<uuid>:1|0`), and `callback_query` calls `decideFromTelegram`, which is the same `decide` the Mac buttons use; the message is edited with the outcome, whoever answered. `scripts/fake_telegram.py` and `scripts/telegram_check.py` run the app against a local fake Bot API (`IRONPET_TELEGRAM_API`, honoured only with `--test-mode`, which also keeps the token in memory).

## Voice notes

Opt-in (`voice.enabled`, off by default). `VoiceController` is one state machine (idle, recording, transcribing) driven by the mic button, the voice hotkey (`hotkeys.voice`, registered only while enabled; `voice.holdToTalk` picks hold-and-release or press-to-toggle, and `RecordingKeys` registers Return and Escape globally only while recording) and the `--test-mode` endpoints under `/test/voice/*`, which feed a WAV file through the same states. `MicrophoneSource` records with AVAudioEngine and converts to 16 kHz mono; `Transcriber` posts the WAV to `{baseUrl}/audio/transcriptions` with `file`, `model` and an explicit `response_format=json` (mlx-audio defaults to `ndjson`). The API key is in the Keychain (`ironpet.voice`), never in config.json. The waveform reads a `LevelBuffer` on its own display-rate timeline, so level updates never re-render the chat. A failed transcription keeps the recording in memory so Retry can re-send it. Recordings are capped at 5 minutes instead of being chunked.

## Meeting transcripts

Opt-in (`meetings.enabled`, off by default; Settings only turns it on after the voice server answers the test clip). `MeetingController` is one state machine (idle, choosing, recording, finishing, summarizing, done) driven by the pet menu, an optional hotkey (`hotkeys.meeting`, no default) and `/test/meeting/*`. Two tracks are recorded: `MicrophoneSource` (Me) and `SystemAudioSource` (Them, ScreenCaptureKit with `capturesAudio`, `excludesCurrentProcessAudio` and an app-filtered `SCContentFilter`, or all system audio). Both implement `StreamingSource`, so samples are handed on as they arrive. A `TrackRecorder` per track (own serial queue) feeds a `Chunker` (closes at the first 0.5 s of silence after the minimum, hard cut at the maximum) and writes `mic-NNN.wav` / `them-NNN.wav`. It pads a stalled source with silence so both tracks stay on one clock, and chunk offsets are sample counts. Each chunk becomes a job: one request at a time, oldest first, `Transcriber.transcribeSegments` (`verbose_json`, one retry with `json` on a 400 or 422, text-only answers become one segment at the chunk start), failures retried with back-off while recording and tried once more after Stop. `MeetingTranscript` shifts segments to meeting time, sorts both tracks and rewrites `transcript.md` after every job. Silent chunks are not uploaded. The summary runs through `CLIBackend` with `RunRequest.readOnly`, which maps to `--tools ""` for Claude Code and `--mode ask --sandbox enabled` for cursor-agent. ironpet writes `summary.md` from the answer. mlx-audio only returns the full payload for `verbose_json` when it has `segments` or `language`, so Parakeet (which returns `sentences`) comes back text-only there; `sentences` only appears with `response_format=ndjson`.

## Testing

`python3 scripts/e2e.py [scenario ...]` (cursor, claude, auto, picker, iterm, capture, summaries, notification, setup, settings; mcp, sentry, voice, voice-key and meeting only when named) relaunches the installed app with `--test-mode`, which enables token-protected `/test/*` endpoints that drive the same code paths as the UI (show chat, send, Allow/Deny, session jump, capture). It runs real cursor-agent and Claude Code turns, checks files on disk and iTerm state via AppleScript, then relaunches the app normally. Test endpoints do not exist outside `--test-mode`.
