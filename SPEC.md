# ironpet v1 spec

A personal macOS desktop pet that floats above all windows, watches coding agents, and runs agent tasks for me.

## Decisions

| Area | Decision |
| --- | --- |
| Audience | Just me. Rough edges are fine. |
| Platform | macOS only, native Swift (AppKit + SwiftUI), Dock app. |
| v1 jobs | Agent watcher, quick chat, screen-aware help. |
| Later | Focus coach, calendar, dev signals, more chat backends, auto-hide. |
| Movement | Stays where dragged (position persists). Idle animations, eyes follow cursor. |
| Art | Ghost, a chibi white direwolf in a Night's Watch cloak, drawn in code by `tools/make_pet.swift` (alternates: Mochi, a mint wolf, and a hamster, panda, bunny and cat on the same body and poses) into the Codex v2 atlas layout (1536x2288, 8x11 cells of 192x208). |
| Success | I stop alt-tabbing to check agents, fire small tasks from the pet, use screenshot help daily. |

## Agent watcher

- Watches Cursor (IDE chats and CLI) and Claude Code via global hooks that the pet installs itself.
  - Merges into each watched agent's own config, preserving other entries (Superset, Orca): `~/.cursor/hooks.json`, `~/.claude/settings.json`, `~/.codex/hooks.json`, `~/.gemini/settings.json`. GitHub Copilot gets its own file in `~/.copilot/hooks/` and Pi gets an extension in `~/.pi/agent/extensions/` that calls the same hook script. `SessionStore` maps each agent's events (Codex uses Claude's names; Gemini's are BeforeAgent/AfterAgent/BeforeTool; Copilot's are camelCase; Pi's come from the extension). The agents offered are the ones found on this Mac.
  - Backs up each file once to `<file>.ironpet-backup` before the first write. Uninstall removes only ironpet entries.
- Hooks POST to the pet on `127.0.0.1` with a token from `~/.ironpet/token`. The hook never blocks or fails the agent (1s timeout, always exits 0).
- Status per session: `running`, `needsInput`, `done`, `failed`, `idle`.
- Pet shows one mood by priority `needsInput > failed > done > running` with a count badge. Click opens the session list.
- `done` and `failed` stay until acknowledged (clicked, jumped to, or a new prompt starts).
- Speech bubble (and optionally a macOS notification) on entering `needsInput`, `failed`, `done`.
- Jump to source: iTerm tab when the hook saw `ITERM_SESSION_ID`, otherwise the Cursor window for the workspace (`open -a Cursor <root>`). Exact Cursor chat/terminal tab is out of scope.

### Event mapping

| Source | Event | Effect |
| --- | --- | --- |
| Cursor | `sessionStart`, `beforeSubmitPrompt`, `postToolUse`, `afterAgentResponse` | running (headless CLI never fires `beforeSubmitPrompt`) |
| Cursor | `stop` (`status`: completed / error / aborted) | done / failed / idle |
| Cursor | `sessionEnd` | remove unless unacknowledged done/failed |
| Claude Code | `UserPromptSubmit`, `PreToolUse`, `PostToolUse` | running |
| Claude Code | `Notification` (`permission_prompt`) | needsInput |
| Claude Code | `Stop` | done |
| Claude Code | `SessionEnd` | remove unless unacknowledged done/failed |

Cursor also runs Claude Code hooks from `~/.claude/settings.json` ("Third-Party Imports", on by default, always on in cursor-agent), so each Cursor event would arrive twice, the second time labelled Claude Code and often without a folder. The hook script exits early for `claude` when `CURSOR_VERSION` is set (only Cursor sets it for hooks), and the app drops `claude` events whose payload has `cursor_version`.

Known gap: Cursor has no hook for "waiting on the user's approval", so Cursor sessions never show `needsInput`.

## Quick chat (milestone 2)

- ⌥⌘G (or clicking the pet when no watched agent needs attention) opens the ironpet window on Chat, with the input focused. Opening it activates ironpet (and closing it reactivates the previous app), because Wispr Flow (hold fn) finds the focused text field through the frontmost app's Accessibility tree. A dictation shows up as one large insert; with "Send automatically after dictation" on, it sends after 0.8s.
- Agents over ACP (`Chat/ACP/`): `ACPClient` speaks newline-delimited JSON-RPC, `ACPBackend` keeps one process per chat and maps `session/update` onto the chat's events. The agent comes from the catalog in `AgentCatalogData.swift` (generated from the ACP registry) and is chosen in the chat settings. Claude Code, Codex and Pi run through the `.mjs` adapters in `Contents/Resources/acp/` on the user's Node 22+ (or a Bun downloaded on request into `~/.ironpet/runtime`), pointed at the user's own CLI by `CLAUDE_CODE_EXECUTABLE`, `CODEX_PATH` or `PI_ACP_PI_COMMAND`. Executables are found on the login-shell PATH. Model choice is stored per agent; threads store the agent id, ACP session id and folder.
- Working directory: frontmost Cursor window (window title matched against `windowsState.openedWindows` in Cursor's `storage.json`) or iTerm session path (AppleScript `session.path`). The chat never switches folder or session by itself, so the detected folder is not applied. Only the user changes them (New Chat, the folder picker, a saved thread, the agent switch). With no folder chosen yet, a "Which project?" picker (recent folders, "No project" → `~/.ironpet/scratch`, or choose a folder) shows and nothing sends until one is picked.
- Approvals: the agent sends `session/request_permission` with the tool call (`kind`, `title`, `rawInput`) and a list of options. `ApprovalRules` decides whether ironpet answers at once (read, search, think, fetch, read-only MCP verbs, memory-file edits, and everything non-destructive in Auto mode) or shows a card. The reply picks `allow_once` or `reject_once`. Identical repeated requests within a turn share one card. ironpet cannot make an agent ask; an agent that does not send the request runs its tools unprompted.
- Questions: Claude Code only gets its AskUserQuestion tool when the client advertises `elicitation.form`, so ironpet does. The agent then sends `elicitation/create` with a flat `requestedSchema`. `ElicitationForm` (`Chat/ACP/Elicitation.swift`) parses it, `ElicitationCard` draws it (radios for `oneOf`, checkboxes for `items.anyOf`, text fields for the `_custom` Other fields and plain strings, numbers and booleans). Submit replies `accept` with the answers, Skip replies `decline`, and stopping the turn or closing the chat replies `cancel`. A schema ironpet cannot draw (nested objects, arrays of objects, URL mode) is declined and logged. A hidden chat announces the question like an approval. The answered card stays in the transcript.
- Auto mode: per-chat toggle handled in ironpet. The agent stays in its asking mode, ironpet auto-allows, and destructive commands (`rm -rf`, `git reset --hard`, `git push --force`, dropping tables) still require approval.
- Stop sends `session/cancel` and keeps the process. Threads are kept and reopened with `session/load`; the replayed transcript is ignored because the chat already holds it.
- ACP chat runs set `IRONPET_ACP_RUN=1`; the hook script skips them so they do not show up as external sessions.
- Memory: the agent writes editable markdown in `~/.ironpet/memory/` (`me.md` plus one file per project), injected into each chat.

## Screen-aware help (milestone 3)

- ⇧⌥⌘G captures the frontmost window, ⌃⌥⌘G a dragged region (also in the pet's right-click menu). Opens quick chat with the image attached.
- Screenshots go to `~/.ironpet/screenshots/` (last 30 kept), which is passed as `additionalDirectories` where the agent supports it. Images go as ACP image blocks when the agent advertises `promptCapabilities.image`; otherwise the prompt names the file.
- The app is signed with a local self-signed identity (`scripts/make_signing_identity.sh`, run by `install.sh` when missing) so TCC permissions survive rebuilds. `scripts/uninstall.sh` removes hooks and the login item by running the installed binary with `--uninstall` (which reuses `HookInstaller`), then deletes the app, Keychain item and preferences, and asks before deleting `~/.ironpet` and the identity.
- Needs Screen Recording permission (also unlocks Cursor window titles for workspace detection). No app exclusions.

## Pet states

| ironpet state | Atlas row |
| --- | --- |
| idle | 0 idle, plus look rows 9-10 following the cursor |
| working | 7 running |
| needs input | 6 waiting |
| done | 4 jumping once, then 8 review |
| failed | 5 failed |
| listening | 3 waving once, then idle |
| dragged | 1 / 2 running right / left |
| sleeping | idle frame 0, dimmed (no row exists); after 10 min with no activity |
| drinking (water reminder) | 11 sipping from a glass, ironpet extra row |
| stretching (stretch reminder) | 12 arms overhead, side stretch, ironpet extra row |

Rows 11-12 are ironpet additions below the Codex v2 layout, so ironpet's sheet is 1536x2704. Atlases without them (Codex pets, older sheets) play the waving row instead.

Reduced motion: frame 0 only. Pet art is loaded from `pet.sprite` in config.json, else `~/.ironpet/pet/spritesheet.{webp,png}`, else the Ghost sheet bundled in the app (generated by `scripts/bundle.sh` with `tools/make_pet.swift`), else a drawn placeholder.

Pet gallery (`App/PetGallery.swift`, `Pet/PetLibrary.swift`): Settings → Pet lists the six sheets `scripts/bundle.sh` generates into `Resources/pets/`, every valid PNG or WebP in `~/.ironpet/pets/` (same name replaces the bundled pet), and a `pet.sprite` that points elsewhere. Invalid files are skipped. Each tile plays idle, waving, jumping and running with the pet's own `AtlasRow` durations. One 15 Hz timer drives all tiles and a 2 s poll of the folder (names, sizes, dates) reloads it; both run only while the General page of the ironpet window is on screen. Reduce Motion shows idle frame 0 and starts no animation timer. Selecting a tile sets `pet.sprite` and renames the pet only if its name is a built-in pet's name or the previous pet's name. "Add from file…" copies a validated sheet into the folder. "Build a new pet" sends `/ironpet-pets <description>` (`PetPrompt`), installing the skill first through `SkillManager` when no agent has it. The skill holds the atlas layout and finds the generator itself, and a test keeps it in step with `AtlasRow`. `skills/ironpet-pets/SKILL.md` is compiled into `BundledSkillsData` like every skill, so Settings → Skills lists it and auto-update keeps installed copies current, opens the chat without calling `prepareForShow`, so the session and folder stay as they are, and sends it in the current thread. `/test/build-pet` triggers it in test mode. OpenAI's built-in pet art is never used or bundled.

Status of milestone 2: built. Threads are saved to `~/.ironpet/threads/` and reopened from the history menu (reopened with `session/load`). Memory files are created on first use, injected into the first turn of each thread, reachable via `--add-dir`, and edits to them never need approval.

## Additions after v1

- **Agent summaries.** Per turn, the watcher records edited files (Cursor `postToolUse`, Claude `PostToolUse` on edit tools) and the final reply (Cursor `afterAgentResponse.text`; Claude `Stop.last_assistant_message` or the tail of `transcript_path`). The summary is "Edited N files · first sentence of the reply" and is used in done/failed notifications and the session list. Headless cursor-agent sends no reply event, so its summary is files only.
- **Approve from notifications.** Approval notifications (chat hidden) use a category with Allow / Deny actions that call the same `decide` as the chat card; resolving a card clears its notification.
- **Alerts (`Signals/`).** An alert is a `Signal` in `SignalStore`: an id, label, title, subtitle, optional URL, symbol, mood and an optional "Ask Ghost" prompt. Script automations create them with `alert` actions. A new or changed alert gets a bubble (the first script run adds alerts quietly), and the list keeps it until it is dismissed or the script resolves it. The most urgent mood among open alerts sets Ghost's mood and badge. The GitHub and Sentry alerts are script automations (`github-alerts`, `sentry-alerts`, templates in `Automations/AutomationDefaults.swift`), not built-in code, and are not created on a fresh install. The GitHub script runs one `gh api graphql` query per host in `~/.config/gh/hosts.yml` every 2 min (own open PRs with CI rollup and review decision, plus review requests) and keeps each PR's CI and review state in its script state. It alerts on failing CI, changes requested and review requests, resolves them when they clear, and shows a short bubble for CI passed and approved. The Sentry script reads `~/.ironpet/sentry.json` and the Keychain token, queries `is:unresolved firstSeen:-1h` and `is:unresolved is:escalating` with curl, alerts on each issue, and resolves an escalation when it stops. Each alert offers Open, Ask Ghost (prefilled prompt, not auto-sent) and Dismiss.

- **MCP in chat.** Headless cursor-agent loads the user's MCP servers (signed in with `cursor-agent mcp login`). Cursor fires `preToolUse` (`MCP:<tool>`, allowed) and then `beforeMCPExecution` (tool, input, server URL), which ironpet gates; Claude Code tools named `mcp__<server>__<tool>` are gated on `PreToolUse`. Read-only verbs (`get`, `list`, `search`, `find`, `fetch`, `read`, `describe`, `whoami`, `lookup`, `show`, `count`) pass; everything else asks, and in Auto mode still asks if the arguments match the destructive pattern. Sentry: REST API for alert polling, Sentry MCP for "Ask Ghost" investigations.
- **Shared MCP sign-ins (opt-in, `integrations.shareMCPSignIns` in `~/.ironpet/config.json`).** cursor-agent keeps OAuth sign-ins per workspace in `~/.cursor/projects/<slug>/mcp-auth.json` (slug = path with non-alphanumerics as `-`). Before each pet chat run, `MCPAuthSharing` copies every server entry that has tokens (with its client registration) from the most recently modified file into the run's workspace file(s), covering both `/tmp/...` and `/private/tmp/...` slugs. This relies on an internal Cursor file format.
- **Automations (`Automations/`).** Reminders, watchers and scheduled jobs are `Automation` records in `~/.ironpet/automations.json` (trigger `interval`, `daily`, `once`, `poll`, `script` or `stream`; action `bubble`, `prompt`, `shell` or `digest`, none for a script). `AutomationStore` loads and validates the file (unknown keys, bad times, literal secrets and duplicate ids are errors), polls its modification date every 2 s, keeps the last good list when an edit is invalid and shows a bubble naming the problem, and writes `automations.schema.json` beside it. On the first launch without the file, `AutomationMigration` turns `config.json` reminders into three `active` interval automations (water 45, stretch 60, eyes 20, keeping their enabled flags) and, only when they were already on (`integrations.githubAlerts`, or a `sentry.json` present), the GitHub and Sentry alerts into script automations. A fresh install gets the three reminders only, and the welcome window's GitHub tick adds the GitHub automation. A file from an earlier build with `builtin` sources is rewritten to those scripts on load. `AutomationEngine` takes time and idle state through an `Environment`, so tests drive it with a fake clock. Every 30 s `tick()` adds the elapsed keyboard time to each enabled `active` interval unless the system idle time or the gap since the last tick is `idleResetMinutes` (5) or more, which resets them. One is due at its interval, or at 75% of it while a watched agent or Ghost chat is running, and everything at 75% or more goes out in one bubble. Nothing active goes out while the chat is open, an approval is pending or a session needs input. `wall` intervals, `daily` slots (including missed ones after sleep, once) and `once` ignore keyboard time and busy state. A `daily` slot is a wall-clock time (`AutomationEngine.slot(on:hour:minute:)`, `Calendar.date(bySettingHour:)`), so it fires at the set time on a day the clocks change; a time the clocks skip fires at the end of the gap (02:30 becomes 03:00) and one that happens twice fires the first time. A `daily` trigger with `catchUpMinutes` works differently: the engine keeps the last slot it fired per automation (`automation_daily`, migration 410, numbered above every other feature's so a database already past them still gets it) and fires the latest slot at or before now once, if it is newer than the stored one and at most `catchUpMinutes` late (never less than 90 s, three ticks, so 0 means on time only); older missed slots are dropped. Turning it on or changing its trigger stores the latest past slot first, and so does the first launch that finds none stored, so a slot from before that never fires; a later launch catches up a slot missed while ironpet was not running. Done jumps Ghost and Snooze makes the automation due again after `snoozeMinutes`. `reminders.paused` holds all time-based automations; polls keep running.
- **Polls (`Automations/PollEngine.swift`).** A port of the necessary parts of agent-trigger's poll engine: run a shell command or `curl` with a timeout (default 30 s) and a 256 KiB output cap, read items with JMESPath (`items`, `id` and `version` expressions, run in-process by the jmespath.swift package, pinned to 1.0.3 because later versions need Swift 6.2 and CI builds with 6.1; filters such as `[?state=='open']` replace agent-trigger's `where`, and regular expressions are not available), and keep a seen set per automation. The first successful run baselines silently; later runs fire for new ids or a changed `version`. Failed runs never baseline. `cooldownMinutes` drops items that arrive too soon after a fire (recorded as `skipped`). Built-in `github` and `sentry` sources call `GitHubWatcher.poll()` and `SentryWatcher.poll()` on the automation's schedule and report through the alerts list. ironpet does not run, call or read agent-trigger.
- **Database (`Support/Database.swift`).** `~/.ironpet/ironpet.db` is ironpet's common database, on the system `SQLite3` module in WAL mode, opened once by `Database` and passed to the features that use it. It knows no feature. Features contribute ordered `Database.Migration`s (a version number, a name, SQL or a closure); the app passes the combined list to `Database.open`. The runner applies the migrations above `PRAGMA user_version`, each in its own `BEGIN IMMEDIATE` transaction that also stores the new version, so a failing one rolls back and leaves the file at the earlier version. A file from a newer ironpet, or one that fails to migrate, is not touched, and the version is checked before the switch to WAL, so its bytes stay as they were. The app logs it, runs on an in-memory database and says so: `Database.open` returns the reason, the in-memory `Database` keeps it in `unavailableReason`, and `SignalStore.reportIfUnavailable` adds one alert ("ironpet can't open its database", with the reason and the file path) and its bubble. The Tasks section, the Usage tab and the automation log show "Not saved: the database is unavailable" instead of their empty state, and `tasks_*` over MCP and `IronPet tasks` return an error naming the reason. All writes run on one serial queue, each in a transaction. Reads use a second read-only connection on a concurrent queue. Other state stays where it was: `config.json`, `automations.json`, threads and meetings are not in the database.
- **Usage (`Usage/UsageStore.swift`, `App/UsageSettings.swift`).** Migration 100 adds `usage_events`: one row per agent turn or transcription request that ironpet runs itself (chat including Telegram, automation prompts, meeting summaries, voice and meeting transcription), with time, feature, model, and only the numbers the agent or provider reported. Missing numbers stay null and show as a dash. Turn cost is the change in the session's cumulative `usage_update` cost since the last record. After `session/load` with no replayed total, the first total is only a baseline: that turn is priced from its tokens (`Usage/UsagePricing.swift`, listed models only) or recorded without a cost. Migration 101 sets chat rows costing over 20 times their token-implied cost to that value. Agents ironpet only launches or watches record nothing. Rows older than 400 days are deleted at launch and at most once a day after that. Writes go through a background queue. The Usage page in Settings shows Today (charted by hour), 7, 30 or 90 days by feature and model. The chart plots requests, tokens or cost, where cost is the sum of the costs recorded per event and events without one count as 0, with a footnote giving their number. A line above the chart gives today's cost and the range's cost.
- **Automation state (`Automations/AutomationState.swift`).** The first client of the database, with prefixed tables from migration 1: `automation_seen` and `automation_state` (seen sets and poll state), `automation_runs` (the last 20 per automation), `automation_approvals` (SHA-256 of the approved or rejected command or prompt) and `automation_snoozes` (restored on launch). Seen items unseen for 7 days and runs older than 30 days are pruned at launch and on every write, and state of deleted automations is dropped. Definitions never go in the database. Migration 4 adds `automation_logs` (time, duration, outcome, summary, and up to 8 KiB of detail per run), written for every poll and script run and for every service event (reminder fired, shell, prompt). Lines older than `automations.logRetentionDays` (config.json, 14 by default, 1 to 365) are deleted at launch and at most once an hour after that, and each automation keeps at most 2000. `AutomationLogWindow` shows them, filtered by automation or problems only, refreshing every 3 s.
- **Streams (`Automations/StreamEngine.swift`, `StreamProcess.swift`, `EventCoalescer.swift`).** A `stream` trigger runs `command` as `/bin/sh -c` for as long as the automation is enabled and approved, and each stdout line is an event. `StreamProcess` starts it with `posix_spawn` in its own process group (`POSIX_SPAWN_SETPGROUP`, default signals, only fds 0 to 2 inherited, stdin is `/dev/null`), reads stdout and stderr with dispatch sources, and signals the whole group: SIGTERM, then SIGKILL after the grace time (2 s) if any member is left. Children a command leaves behind after it exits are stopped the same way. `StreamEngine` keeps one slot per automation, so a second copy never starts: a changed definition waits for the old process to exit, then starts the new one. It reconciles from `AutomationEngine.set` (file changes, pause, delete), from `AutomationService.approve`, and once from `AutomationService.start`, so nothing starts before the approval check is wired. A stream does not tick. After an exit it restarts with a wait of 1 s doubling to 300 s, reset by a run of 60 s or more; exits, restarts and their reasons go to the history and the execution log (nonzero exits as `failed`). A line goes through `PollExtractor` (one line at a time, mode `lines` by default or `json` with `items`, `id`, `version`), then `when` (JMESPath truthiness, `JMES.truthy`), then the rate limit (20 events a second, counted after the filter), then the seen set (only when `id` is set, kept in `automation_seen`, saved at most every 30 s and when the process exits, capped at 5000 ids; it starts empty on the first run and is not a baseline), then `cooldownMinutes`, then `EventCoalescer`. The coalescer is not stream specific. It holds the newest pending event with a count, fires after `debounceSeconds` of quiet, at most once per `throttleSeconds`, and never while the previous fire's action is running. `AutomationService.handle` passes `Fire.finished`, which a shell or background prompt action calls when it ends; bubbles and chat prompts finish at once. `{{count}}` is the merged count. Lines over 64 KiB, events over the rate and events inside a cooldown are dropped and summarised once a second in the log, and stderr is logged in the same summary, never an event. App quit calls `AutomationService.stop`, which sends SIGTERM to every group, waits up to 2 s and sends SIGKILL, so a stuck child cannot hold up the quit. `automations_get` adds `stream` (`running`, `restarting` or `stopped`) and `lastEvent`, and Settings shows the same on the row. A stream command is risky text (`stream:` plus the command), approved like a shell command.
- **Scripts (`Automations/AutomationScript.swift`).** A `script` trigger runs `poll(state)` in QuickJS (zqqf16/QuickJS-Swift, which vendors the official QuickJS), in the main process, on a background queue. A script automation has no `action` (stored as type `none`, left out of the file). The runtime is created with `enableStdModules: false`, so there is no `std`, `os`, file loader or worker, and no `fetch`, timers or `require`. The prelude module gives the script `sh(command, options)` and `console.log`, which call `HostIO`. A script that needs the network runs `curl` through `sh`. Limits: 32 MiB of memory (`JS_SetMemoryLimit`), an interrupt handler that stops the script after 60 s, 8 `sh` calls per run with each timeout capped at the time left and output capped at 256 KiB, 64 KiB of script, 256 KiB of state, 20 actions. `poll` must be synchronous. It returns `{state, actions}`. The state goes to `automation_script_state`. Each action has a type of `bubble`, `alert`, `prompt` or `suggest_task`, and the engine carries it out (`AutomationService.perform`). The script cannot cause a side effect itself, and there is no `shell` action because a script can already call `sh`. A `bubble` is an `AutomationNotice` (same `id` replaces it). An `alert` becomes a `Signal` of kind `automation` in the alerts list, with its own label, symbol and mood from `severity`. A hash of each alert as last shown is in `automation_alerts`: a new or changed alert notifies, one listed again unchanged is left alone even if the user dismissed it, `resolved: true` removes it, and the first run adds alerts quietly. A `prompt` runs through `AutomationPrompt`. A `suggest_task` (`id`, `title`, `due`, `notes`, `url`) is read by `TaskSuggestion.Draft(action:)` and handed to `TaskStore.suggest(_:automation:name:)` (see Tasks); it never creates a task. A script an agent wrote counts as risky text, so its hash needs approval like a shell command. The validator loads the script once in a sandbox that cannot run commands, and requires a `poll` function.
- **Daily brief (`Brief/`, `Pet/TodayView.swift`).** Built-ins `morning-brief` (09:00, `catchUpMinutes` 180) and `day-recap` (18:00, 120), weekdays, off, `createdBy: user`, with a `digest` action (`brief` or `recap`) that has no risk text, so no approval. `BriefBuilder` is pure: `BriefInput` (now, calendar, tasks, sessions, alerts, meetings, activity) in, `Brief` (sections of items, each with a `Target`: task, session, alert or meeting; and at most four bubble lines) out. The brief covers due or overdue open tasks, tasks that need the user, alerts whose mood is not `done` ordered review requested, CI failed, changes requested, unticked action items owned by Me or nobody from meetings since the previous allowed weekday (an item matching a done task is dropped, one matching an open task targets it), and sessions needing input or failed. The recap covers today's activity (turns done and failed, alerts resolved), tasks closed today, today's meetings, and still open (needs you and in progress tasks, alerts, waiting agents), whose line is always kept. `BriefSource` gathers the input on the main actor from `TaskStore`, `SessionStore`, `SignalStore` and `~/.ironpet/meetings` (open action items are cached per summary by modification date) and reads today's turns and resolved alerts from `ActivityLog` through `BriefActivitySource` (`session.done`, `session.failed` and `alert.resolved`, with the workspace, app and iTerm session from `extra`, so an ended session still reopens); without the log, as in previews, it uses the done and failed sessions still in `SessionStore`. It stores nothing of its own. `AutomationService.handle` builds the brief through `digest`, records `ok: nothing to report` for an empty scheduled one, and otherwise calls `showDigest` (`Fire.manual` is set by Run now, which shows an empty one too). It passes `Fire.slot`, so a recap caught up after midnight covers the slot's day from its start (`BriefInput.day`) and its bubble carries that date. Its Open passes that day to `BriefModel.show(recapDay:)`, so the Today recap stays on it until the user picks a kind on the page or the page closes. `Announcer.briefBubble` uses id `digest:brief` or `digest:recap`, a date subtitle, an Open button and tap, and expires at the next midnight (15 s when empty, or `presentation.expiresSeconds`). The Today section is the last sidebar row, listed only while an enabled automation has a `digest` action (`IronPetWindowModel.todayShown`; Open from Run now on a disabled one shows the page without listing it), hides bubbles, is never picked by `needingAttention`, and shows a Brief/Recap picker over the sections from `BriefModel`, which rebuilds on appear and, while visible, 400 ms after a store change (visible is Today selected in an open window: the page's appear and disappear cover section changes, and `PetController` passes the panel's visibility change, since closing the reused panel fires neither). A row opens its task (Tasks scrolls to and highlights it through `focusTask`), its session (the live one jumps; an ended one opens its folder in the app it ran in), its alert link (or Alerts), or its meeting (Transcripts selects it through `focusMeeting`). Settings › Automations shows a time picker for a daily automation with one time, and Weekdays only when its days are every day or Monday to Friday (`DailySchedule`).
- **Heartbeat (`AutomationDefaults.heartbeat`, `HeartbeatChecklist`).** Id `heartbeat`, `createdBy: user` (no approval), `interval` 15 min `wall`, `prompt` action `/heartbeat` with `quiet` `HEARTBEAT_OK`. `AutomationStore.init(builtIns:)` appends a built-in whose id is missing from the file, for a new and an existing file, and leaves one that is there as the user set it (so a switch-off persists). ironpet no longer adds `review-tasks`, and does not migrate or remove one that is in a user's file. ## Tasks

The agent's board, not the user's: the agent keeps track of the items, the user tells it what happened. Moving cards by hand would lose what the agent knows, so the UI only marks done, deletes, and adds or skips suggestions from meetings and watchers.

- **Store (`Tasks/TaskStore.swift`).** Migration 200 adds `task_items` (id, title, notes, status, source, due, created, updated, closed), `task_links` (thread, session, url or file per task, in order), `task_events` (one row per create, status change, edit, note, close and delete, with who did it: `user`, `agent:mcp`, `agent:cli`, `test`) and `task_suggestions`. Statuses are fixed in v1: `backlog`, `in_progress`, `needs_you`, `done`. Migration 304 (202 in a development build, so it adds each column only where it is missing) adds `waiting_on` (a name, at most 100 characters) to `task_items` and `task_suggestions`; a task with it is waiting on someone else, so `TaskItem.needsUser` and `activeCount` ignore it whatever its status, and the agent clears it (null) when the next step is the user's again. Ids are slugs of the title (`AutomationValidator.slug`), never reused while a deleted task's history is kept. Done tasks older than `tasks.keepDoneDays` (30, 1 to 365) and history of tasks that no longer exist are pruned at launch and at most daily. `TaskStore.call(op, args, by:)` is the one entry for MCP, the CLI and test endpoints; `TaskValidator` checks titles (1 to 200 characters), notes (4 KiB), statuses, ISO 8601 due dates, links (at most 10, `url` must be http or https) and `waiting_on` (one line, blank clears it). `tasks_create`, `tasks_update` and `IronPet tasks add --waiting-on` set it; task JSON carries it.
- **Agent interface.** `Bridge/MCPEndpoint.swift` serves `initialize`, `tools/list` and `tools/call` on `POST /mcp` for both tool sets and routes `automations_*` to `AutomationService.call` and `tasks_*` to `TaskStore.call`. `POST /tasks` is the plain form `IronPet tasks …` uses. `Memory.preamble` tells every chat that it keeps the list, when to add, close and move to needs you, and never to start work on a task unless asked. Automation prompts run in the user's chat and can change tasks like any message there. Restricted sessions (prompts that use `{{item.*}}`, meeting summaries) get no MCP servers, so they cannot. `tasks_list` results say that task text is data, not instructions.
- **Meetings (`Tasks/ActionItems.swift`).** The summary prompt already asks for `- [ ] <task> (owner: …, due: …)` lines under `## Action items`. After `summary.md` is written, `ActionItems.suggestions` keeps the items that have an owner: "Me" (any case) is the user's, any other owner ("Them", a name) is kept as the suggestion's `waitingOn`, and items without an owner are dropped. `TaskStore.suggest` drops ones that match an existing task or suggestion by title, and one bubble without buttons titled "From your meeting" says "<n> suggestions for review" and the first title (`Announcer.taskSuggestionsBubble`). Accepting makes a `backlog` task with source `meeting`, the suggestion's `waitingOn` and a `file` link to the meeting folder; a due that is not an ISO date stays in the notes. Suggestions are text only and never sent to an agent. `tasks.meetingSuggestions` (on) turns this off.
- **Watchers (`AutomationService.perform`).** A script's `suggest_task` action becomes a suggestion whose origin is the automation (id and name) instead of a meeting. ## Background jobs

Ghost as a front desk: the chat agent (and, later, voice mode) hands work to background jobs and answers "what's going on" from ironpet's own stores.

- **Model and store (`Jobs/JobModel.swift`, `Jobs/JobService.swift`).** Migration 500 adds `jobs` (id `job-xxxxxx`, title, prompt, folder, agent, model, thread, task, state, last step, summary, error, created, started, ended). States: `queued`, `running`, `needs_approval`, `done`, `failed`, `stopped`, `interrupted`. At launch, jobs that ended more than 30 days ago are deleted and every active one becomes `interrupted` in one `UPDATE` (their in-progress task goes back to `backlog`). In memory: the active jobs and the newest finished ones, 50 in all.
- **Running.** `JobService.start` validates (title 1 to 120 characters, prompt up to 20,000, an existing folder), creates an `in_progress` task with source `agent`, and queues the job. `pump` starts queued jobs, oldest first, while fewer than `jobs.maxRunning` (3, clamped to 1 to 5) hold a process. Each gets its own `ACPBackend` (`JobAgent` protocol, faked in tests) with `usageFeature = .jobs`, the chat's agent and model, and a first-turn preamble: `JobService.instructions` (unattended, no questions, stay in the folder, no pushes or messages unless asked, end with a one-sentence result) plus `Memory.preamble`. Elicitations are declined. Each turn has a 60-minute watchdog that cancels it and fails the job. Events go through `TranscriptRecorder` (shared with `AutomationSession`); the thread is saved under the ACP session id with `ChatThread.job`, and the task gets a `thread` link. The job ends `done` with the first sentence of the reply as its summary (task closed), `failed` (task `needs_you` with the error), or `stopped` (task closed).
- **Approvals.** Permission requests get `ApprovalRules.policy(for:auto: true)`. What still asks (destructive commands and tools) moves the job to `needs_approval` and shows an Allow / Deny bubble (`AutomationNotice`, no expiry). Only a click answers it. Opening the job shows a closed bubble again; stopping the job or the end of the turn takes it down and denies.
- **Follow-ups and stop.** `followUp` queues a message for a running job (sent after its turn, same process) or requeues a finished one, which resumes the session (`session/load`) without a preamble. `stop` drops a queued job, or cancels the running turn (`session/cancel`), denies its pending approvals and shuts the process down.
- **In the app.** `Job.agentSession` maps a job to an `AgentSession` with source `job` ("Background job") under the key `job:<id>`, set through `SessionStore.setJob`: queued and running show as running (detail "Waiting to start" or the last step), `needs_approval` as needs input with "Wants to: …", done and failed as themselves, stopped and interrupted are removed. Hook events with source `job` are ignored, and `sweep` skips jobs. `onAttention` records activity as for any session; a job's needs input shows no session bubble, because the approval bubble covers it. A click on the row, the bubble or a brief item opens the job's thread in the chat (`PetController.onOpenJob`). While the job runs, `ChatSession.jobFollowUp` sends a message typed in that thread to the job instead, and `threadSaved` refreshes the open thread as the job writes it, keeping typed messages the job has not started on yet. The job saves its thread when each turn starts and ends. Its prompts carry origin `job` ("Background job" under the message).
- **Tools (`Jobs/AssistantMCP.swift`, routed by `MCPEndpoint` through `AssistantContext`).** `jobs_start(title, prompt, folder)`, `jobs_list(include_older?)`, `jobs_get(id)` (with the last 8 transcript steps), `jobs_followup(id, message)`, `jobs_stop(id)`, `jobs_open(id)` (refused while the chat is running a turn, since opening a thread ends it). `projects_resolve(name?)` returns `best`, `matches` and `ambiguous` from `ProjectResolver`: candidates are the front Cursor window's folder (`WorkspaceDetector`; iTerm is not asked, since that is an Apple Event on the main thread), the chat's folder, Cursor's open folders (`storage.json`), the folders of watched agent sessions, recent chat folders and the no-project folder, compared by standardized path (Cursor's URLs end in a slash), missing folders dropped. Names are compared as lowercase letters and digits after dropping filler words ("the", "repo", "project"): same name 3, containment 2, same first three letters 1, and a single top score wins. `jobs_start` only accepts a candidate's path. `status_overview`, `status_sessions`, `status_alerts`, `status_today(kind)` and `status_meetings(limit?)` read `SessionStore` (jobs left out), `TaskStore`, `SignalStore`, `BriefSource` and `MeetingLibrary` (with `ActionItems.openItems` of each summary). `memory_recall`, `memory_remember(text, kind, workspace?)`, `memory_forget(text)` and `memory_list(kind?)` go to `MemoryStore`. Everything but `jobs_start`, `jobs_followup` and `jobs_stop` is in `ApprovalRules.ownTaskTools`.
- **Job scope.** A job's session gets ironpet's MCP entry with `IRONPET_MCP_SCOPE=job`, so its stdio bridge posts to `/mcp/job`, which leaves `jobs_start`, `jobs_followup`, `jobs_stop` and `jobs_open` out of `tools/list` and refuses them. A job cannot start or steer jobs.
- **Memory (`Chat/MemoryStore.swift`).** `MemoryStore` is the interface (recall, remember, forget, list) so another memory module can replace the files. `FileMemoryStore` writes bullets to `me.md` (fact), `people.md` (person), `conversations.md` (conversation, stamped `yyyy-MM-dd HH:mm`, last 50 kept) and the project file (`Memory.projectFile`). A line is whitespace-collapsed, at most 500 characters, refused when `CaptureRedactor` finds a secret, and skipped when it repeats one (case-insensitive). `forget` needs 3 characters and refuses to remove more than 10 lines. `Memory.preamble` adds `people.md` when it has bullets.

## Telegram

Opt-in (`telegram.enabled`, off by default). `TelegramBridge` long-polls `getUpdates` (30 s, offset in UserDefaults; a new bot's backlog is skipped) through `TelegramAPI`, which takes the token from the Keychain (`ironpet.telegram`) on every call. Messages from ids in `telegram.allowedUsers` go to `ChatSession.submitFromTelegram`, which adds a user item with `origin: "telegram"` to the current chat and never calls `use` or `newChat`; a busy agent queues it and the queue drains when the turn ends. `ChatSession.onTelegram` reports started, waiting for approval, finished(last assistant text) and failed for turns that began in Telegram, and the bridge sends typing every 4 s and the answer through `TelegramFormat` (Markdown to Telegram HTML, split on converted length, code blocks closed and reopened across parts, plain-text retry on a 400). Pairing: with nobody allowed, a `/start` from a private chat becomes a pending request (max 3) and a bubble. Errors set the status line and back off 2, 4, … 300 s. Uploads: `TelegramMediaStore` picks the largest photo size, documents and videos as files and voice, audio and video notes as voice, refuses over 20 MB before and after `getFile`, and saves under `~/.ironpet/telegram/files/<chat>/<stamp>-<id>/<name>`; messages with a shared `media_group_id` in one poll become one chat message. Incoming work with files runs through one in-order queue so text sent after a download does not overtake it. Voice goes through `TelegramVoice` (AVFoundation to 16 kHz WAV when it can decode, else the raw file with its MIME type) and the Settings → Voice server; the transcript is echoed as `🎙 text` and sent as the message text. Approvals: `ChatSession` emits `approval` and `approvalDecided` for Telegram-started turns, the bridge sends Approve and Reject inline buttons (`a:<uuid>:1|0`), and `callback_query` calls `decideFromTelegram`, which is the same `decide` the Mac buttons use; the message is edited with the outcome, whoever answered. `scripts/fake_telegram.py` and `scripts/telegram_check.py` run the app against a local fake Bot API (`IRONPET_TELEGRAM_API`, honoured only with `--test-mode`, which also keeps the token in memory).

## Voice notes

Opt-in (`voice.enabled`, off by default). `VoiceController` is one state machine (idle, recording, transcribing) driven by the mic button, the voice hotkey (`hotkeys.voice`, registered only while enabled; `voice.holdToTalk` picks hold-and-release or press-to-toggle, and `RecordingKeys` registers Return and Escape globally only while recording) and the `--test-mode` endpoints under `/test/voice/*`, which feed a WAV file through the same states. `MicrophoneSource` records with AVAudioEngine and converts to 16 kHz mono; `Transcriber` posts the WAV to `{baseUrl}/audio/transcriptions` with `file`, `model` and an explicit `response_format=json` (mlx-audio defaults to `ndjson`). The API key is in the Keychain (`ironpet.voice`), never in config.json. The waveform reads a `LevelBuffer` on its own display-rate timeline, so level updates never re-render the chat. A failed transcription keeps the recording in memory so Retry can re-send it. Recordings are capped at 5 minutes instead of being chunked.

Spoken replies are a separate opt-in (`speech.enabled`, off by default) on the same server and key. `ChatSession` marks every turn sent from the chat (not from Telegram or an automation), and when that turn finishes without an error calls `SpeechPlayer.speak` with the last reply, unless `isQuiet` says a meeting is recording or another app holds the microphone (`Presence` over a `MicWatch` that `AppDelegate` keeps polling only while the feature is on, because its first answer is always empty). Dictation apps (Wispr Flow, Siri, macOS dictation) never count as holding the microphone, here or for the meeting call offer (`CallApps.ignoredPrefixes`). A speaker button on each reply, its context menu and `/test/speech/speak` call the same player. `SpeechText` keeps headings, paragraphs, quotes and list items from `Markdown.parse`, drops code, tables, rules, bare URLs and emoji, splits sentences with `NLTokenizer` and stops at the sentence that reaches 900 characters (about a minute); the first chunk is one sentence and later ones are grouped up to 220 characters. `SpeechPlayer` synthesizes the first chunk, plays it with `AVAudioPlayer` while the next is synthesized, and cancels both on stop. Sending a message, starting a voice note, Esc in the chat and turning the feature off all stop it. `Synthesizer` posts JSON to `{baseUrl}/audio/speech` with `response_format: "wav"`; an empty 200 body is reported as missing audio, because that is what mlx-audio returns when Kokoro cannot load without `misaki`. Settings lists voices from mlx-audio's `GET /audio/voices?model=` and falls back to a text field for servers without it (OpenAI), and the switch turns on only after Preview plays, like the Meetings switch.

## Screen capture

Opt-in (`screenCapture.enabled`, off by default). `CaptureService` is the master switch: with it off no source, timer, event monitor or permission request exists. With it on, in order:

1. **Triggers** (`CaptureSource`, macOS: `AXCaptureSource`; `CaptureScheduler`). Capture is event-driven. Signals are app activation (`NSWorkspace`), focused-window and title changes (`AXObserver` on the front app, on the main run loop), and global `NSEvent` monitors for key, scroll and click, used as timing only. `CaptureScheduler` is a pure struct with a caller-supplied clock. A signal sets a settle time: 0.3 s for an app switch or window focus change, 0.5 s after the last key, 0.4 s after the last scroll, 0.2 s after a click. A key or scroll pushes its own pending capture back, so a burst makes one capture. Every 10 s with nothing pending, an idle capture fires. Two captures are never closer than 0.2 s. The service arms one timer for the next due time and reads on the `ironpet.capture` utility queue.
2. **Privacy gate** (`CapturePrivacy`, `CaptureFloor`, `CaptureURL`). Swift code no setting can change: pause, lock screen, a fixed app and host denylist (password managers, authenticator apps, loginwindow, HTTP proxies), private browser windows by title, URL scheme and host checks, and URL secret stripping. The user's `excludedApps` list adds to it.
3. **Read** (`CapturePipeline`, `CaptureText`). `readFocusedWindow` walks the focused window's tree into `AXNode` values, within 6,000 nodes or 200 ms, whichever comes first, and takes what it read. A secure text field is read for role and subrole only. A button, menu, toolbar, tab, checkbox or similar control is read for its name and page id, never its children, and `CaptureText.lines` drops it. Every element also reads `AXDOMIdentifier`. The text of static text, headings, text areas and text fields is kept as lines. Chromium and Electron apps get `AXManualAccessibility` so they build their page tree. The page address is the first web area's `AXURL`. There are no per-app parsers.
4. **Screenshot fallback** (`ScreenOCR`). When the walk yields no lines and `screenCapture.ocr` is on and Screen Recording is granted, `ScreenOCR.screenshot` captures the app's largest window with `SCScreenshotManager` into a `CGImage`, Vision's `VNRecognizeTextRequest` reads it, and the image is released. It is never written to a file. With the fallback off, such a window stores nothing. Turning the fallback on is what asks for Screen Recording.
5. **Tree store, blocks and drafts** (`CaptureTree`, `CaptureBlocks`, `CaptureTreeStore`, `CaptureStore.ingest`, tables `capture_window`, `capture`, `capture_fts`, `capture_node`, `capture_block_seen`, `capture_draft`, migration 442). `CaptureTree.prepare` drops hidden elements, keeps role and subrole of a secure field, runs every text through `CaptureRedactor` and `CapturePrivacyFilter.filterOnWrite`, and hashes bottom-up: a node is `["<child hashes>", role, subrole, title, value, description, url, domId]` JSON, its key the first 9 bytes of SHA-256 in base64url (12 characters). Nodes are not compressed: a capture's new nodes are a few KB of mostly unique hashes and short texts, which per-row zstd or LZFSE shrinks too little (LZFSE on a packed capture saved about 40%, and a shared dictionary needs a blob column the database layer does not bind). `capture.root` holds the root hash. A new capture writes only the nodes not stored yet (`CaptureStore.lastNodeWrites`). Reading rebuilds a tree with one query per level. `CaptureBlocks.extract` finds blocks by shape: role Group with subrole DocumentArticle, list items and rows, outermost first. A block's label is its accessible name when that name holds text from inside the block, else a line from its own text (headings by name, texts that most sibling blocks repeat left out, siblings meaning blocks that share a list through any single-child wrappers). `when` is the longest text in the block with a four-digit year. Identity is the page id (of the block, or of a wrapper whose only child it is), else a hash of the text. `capture_block_seen` gets a row when a block is new (not seen in the same window in the last 7 days), edited (same page id, different text) or sent. A capture row is stored only when a block changed. A tree that differs only in the text of input fields stores nothing and updates `capture_draft`, one row per field, keyed by page id, else name, else tree path. When a field empties and a new block holds its text, the draft is `sent` and the block's kind is `sent`; with no match in 120 s the draft is `discarded`. `capture.text`, which `capture_fts` indexes, holds the labels and text of the changed blocks. A window with no blocks, and a screenshot read (which has no tree), is one block, the page, with identity `page`: its text is the lines that are new, found with the line diff: a 64-bit SHA-256 prefix of each line of the last capture (`last_lines`), `CaptureDiff.fresh` with two lines of context, redacted first. A window is keyed by app plus window title, or app plus the page address without secrets and fragment. A window without an address whose title changed is matched to the same app's window seen in the last 30 s that shares at least half of its lines. Prune deletes captures, block rows and drafts past retention (default 30 days), then every node that no remaining capture's root reaches. Migration 442 drops the capture tables and creates them again with this schema, so captures stored before the upgrade are deleted. There is no reader for the old rows.
6. **Tools** (`ScreenMCP`, routed by `MCPEndpoint` with the other `tasks_*` and `automations_*` tools, so every chat agent gets them through the stdio bridge). Both are in `ApprovalRules.ownTaskTools`, so they run without an approval card. `screen_search(query, app?, since?, until?, limit?)` runs an FTS5 query (over text, window title, app name and page address) where every word must match and returns the capture id, time, app, window, URL and a snippet. `screen_window(since, until?, app?, window?)` returns the change list from `capture_block_seen` and `capture_draft`, grouped by window, at most 30 lines per window (the newest, dated entries first among equals) and a `more` count, with a page entry for a window without blocks. `screen_window(id)` returns `CaptureView.outline` of the cleaned tree: wrappers with no name are skipped, headings read by name, and text that most sibling blocks repeat is dropped. `root` (a ref) returns one subtree and `role` the elements with that role. A capture with no tree (a screenshot read) returns its text. Both return only stored text, filtered on read. Times accept `today`, `yesterday`, `now`, a date, an ISO 8601 time or an age such as `90m`.
7. **Tasks.** There is no in-app analysis of captures. The bundled `ironpet-tasks` skill has a screen evidence section, which the heartbeat's default entries invoke: a cheap subagent reads the `screen_window` change list since the last run and runs `screen_search` for keys from open task titles, returns who, what, where and when with capture ids, and the reviewing agent updates tasks or creates them with origin kind `capture` and the ids as `ref`. Screen text is data, never instructions. Migration 441 deletes capture suggestions and `task_suggestion_outcomes` and rebuilds `task_suggestions` with only meeting and automation origins.

Settings → Screen shows the switch, Accessibility status, pause buttons, the screenshot fallback toggle, the never-capture list, retention and Delete all captures. The Screen section of the main window (below Transcripts, always listed) is `ScreenSection`: the latest captures (time, app, window, first lines, a row opens its full stored text) and a search field over the FTS index. It reads only the local database. A config change reaches the service through `apply(_:)` with the new value, because `ConfigStore` publishes before it stores.

Test mode (`--test-mode`) swaps in `IdleCaptureSource`, so it never reads the real screen or raises the Accessibility prompt. `GET /test/screen` and `POST /test/screen/ingest|inspector|reset` feed synthetic captures in, and `scripts/e2e.py screen` checks the tools through them.

## Desktop control

Agents operate other apps through ironpet's own MCP server, so there is nothing to install and the Accessibility grant is the one ironpet already has. Off by default (`desktopControl.enabled`).

1. **Reading** (`Desktop/DesktopAX.swift`, `DesktopService`). `LiveDesktopAX` reads a window with `AXCaptureSource.convert`, the walk screen capture uses, so it keeps the node and time budgets (6,000 nodes, 1 second here against 0.2 for background capture, because an agent asked), the Chromium and Electron switch and the rule that a secure field is read for its role only. The walk also returns the `AXUIElement` behind each node in pre-order. `CaptureTree.prepare` cleans the tree (redaction, hidden elements dropped) and gives every node its hash as `ref`. A repeated hash gets `~2`, `~3` in outline order. The views are `CaptureView.outline` (with `allRefs`, so a leaf button has a ref), `CaptureView.find` and `search`. The sibling-text pruning of `CaptureView.cleaned` is not applied, because a control that repeats is exactly what an agent needs to press.
2. **Refs.** `DesktopService` keeps the table ref to element for the last read of each window, replaced on the next read. An entry also keeps a key: the hash of the element's own cleaned role, subrole, title, value and description (the value of an input is left out, so typing does not stale it). Before an action the service reads the element's own fields again and compares the key. A different key, a gone element or an unknown ref fails with "take a new desktop_snapshot".
3. **Actions.** AX actions, except `desktop_key` (item 8). `press` picks AXPress, else AXConfirm, AXPick or AXOpen. `set_value` sets AXValue when it is settable. `type` focuses the element, inserts through AXSelectedText when it is settable, and otherwise appends to AXValue. `focus` sets AXFocused, or raises a window with AXRaise and AXMain.
4. **Gate** (`DesktopSafety`, `DesktopService.check`). The checks run twice, before the question and after the answer, so an element that changed while the user decided does not run. They are: the app is not ironpet and passes `CapturePrivacy.checkApp` (pause, lock, user exclusions, the hard-coded deny list), the window is not private and passes `CapturePrivacy.check` (address rules for a browser), the element is not a secure field, and the ref is current. A generic verb list (send, pay, delete, submit, buy and forms of them) in the element's name, its value (unless it is an input) or the window title requires an approval. The code names no app, and `DesktopControlTests.testDesktopCodeNamesNoApp` scans the folder like the capture code's test.
5. **Approval.** `DesktopApprovals` shows an `AutomationNotice` with Approve and Reject, the same bubble the automation approvals use, and answers no after 120 seconds. The chat's `ApprovalRules` treat the `desktop_*` tools like any other MCP tool, so they also ask in the normal mode.
6. **Log.** Each attempt that reached a resolved element is recorded as an `ActivityEvent` of kind `desktop.action` (outcome `done`, `failed`, `declined` or `refused`), kept 30 days, and listed in Settings → Screen.
7. **Screenshots.** `desktop_screenshot` reads the window first, so the same rules apply, then needs `CGPreflightScreenCaptureAccess`, takes the window by its window id with ScreenCaptureKit (`ScreenOCR.screenshot`), scales the long edge to 1,600 pixels and returns a PNG as an MCP image content block. It is never written to disk.

8. **Keys and addresses.** `desktop_key` parses lowercase names joined by `+` (`DesktopKeys`), runs the same app, window and password-field checks as the other tools, raises the app when it is not frontmost, and posts key down and key up with `CGEvent.postToPid`, never to a system-wide tap. `DesktopSafety.keyApprovalReason` decides approval: Cmd+Return, Cmd+Q and Cmd+W always ask, and Return or a Cmd combo asks when the focused window title or focused element text has a risky verb. The focus is read again after the answer, and a key that now needs approval but was not asked about is refused. `desktop_open_url` accepts http(s) only, no user name or password, a host that passes `CaptureFloor.checkURL`, and opens through the `DesktopOpener` protocol (named browser, else the frontmost browser, else the default).
9. **Select, check, expand.** `select` finds options live through `AXChildren` (menu items, rows, radio buttons, tabs), opens a popup first, needs one match, and refuses an option whose own label has a risky verb unless the user approved. `check` reads the value, presses only when it differs, and reads it again. `expand` sets AXDisclosing or AXExpanded when settable, else presses a disclosure triangle, else opens or cancels a popup.

Test mode swaps in `IdleDesktopAX` and `IdleDesktopOpener`, so an automated run never touches the real screen.

## Meeting transcripts

Opt-in (`meetings.enabled`, off by default; Settings only turns it on after the voice server answers the test clip). `MeetingController` is one state machine (idle, choosing, recording, finishing, summarizing, done) driven by the pet menu, an optional hotkey (`hotkeys.meeting`, no default) and `/test/meeting/*`. Two tracks are recorded: `MicrophoneSource` (Me) and `SystemAudioSource` (Them, ScreenCaptureKit with `capturesAudio`, `excludesCurrentProcessAudio` and an app-filtered `SCContentFilter`, or all system audio). Both implement `StreamingSource`, so samples are handed on as they arrive. A `TrackRecorder` per track (own serial queue) feeds a `Chunker` (closes at the first 0.5 s of silence after the minimum, hard cut at the maximum) and writes `mic-NNN.wav` / `them-NNN.wav`. It pads a stalled source with silence so both tracks stay on one clock, and chunk offsets are sample counts. Each chunk becomes a job: one request at a time, oldest first, `Transcriber.transcribeSegments` (`verbose_json`, one retry with `json` on a 400 or 422, text-only answers become one segment at the chunk start), failures retried with back-off while recording and tried once more after Stop. `MeetingTranscript` shifts segments to meeting time, sorts both tracks and rewrites `transcript.md` after every job. Silent chunks are not uploaded. The summary runs through `CLIBackend` with `RunRequest.readOnly`, which maps to `--tools ""` for Claude Code and `--mode ask --sandbox enabled` for cursor-agent. ironpet writes `summary.md` from the answer. mlx-audio only returns the full payload for `verbose_json` when it has `segments` or `language`, so Parakeet (which returns `sentences`) comes back text-only there; `sentences` only appears with `response_format=ndjson`.

Regenerate (`MeetingRegenerator`, owned by `MeetingLibrary`) rebuilds a finished meeting from its folder, not through `MeetingController`, which only knows the meeting being recorded. `MeetingFolderScan` lists `mic-NNN.wav` and `them-NNN.wav`, takes each chunk's length from its samples, and adds the lengths of earlier chunks of the same track as the offset, which is how `TrackRecorder` counted them. The start time comes from the folder name (minute) and the first chunk's modification time minus its length (second), used only when it falls in that minute; the app name comes from the old transcript's header. Full mode sends the non-silent chunks one at a time in meeting order through the same `Transcriber`, the same diarizer, `MeetingSpeakerTable` and a final `relink` against the current voice store, so it names voices the way a live meeting does but forgets names typed for voices that are not in the store. A failed chunk, an empty transcript or a failed or empty summary throws before any file is touched. The write is two steps: new text goes to `*.new.md`, then each file is moved to `*.prev.md` (replacing the last one) and its `.new.md` moves into place, undoing the finished moves if one fails. Summary-only mode summarises `transcript.md` as it is, which already holds names from `nameSpeaker`. The summary goes through `MeetingSummaryRun`, the same read-only agent setup as `MeetingController.summarize`. `ActionItems.carryChecked` ticks items of the new summary whose normalised text was ticked in the old one, and `ActionItems.newSuggestions` limits task suggestions (the user's own and the ones they wait on) to items the old summary lacked; `TaskStore.suggest` compares titles with the same normalisation. After a speaker is named, `SpeakerPrompt` shows "Regenerate summary" (`MeetingController.canRegenerateSummary`), which runs summary-only mode. Nothing regenerates automatically.

## Testing

`python3 scripts/e2e.py [scenario ...]` (cursor, claude, auto, picker, iterm, capture, summaries, notification, setup, settings; mcp, sentry, voice, voice-key and meeting only when named) relaunches the installed app with `--test-mode`, which enables token-protected `/test/*` endpoints that drive the same code paths as the UI (show chat, send, Allow/Deny, session jump, capture). It runs real cursor-agent and Claude Code turns, checks files on disk and iTerm state via AppleScript, then relaunches the app normally. Test endpoints do not exist outside `--test-mode`.
