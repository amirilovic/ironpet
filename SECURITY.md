# Security

ironpet runs on your Mac with your user's permissions, watches your coding agents, and can start agents that edit files and run commands. This page lists what it touches and what protects it, so you can decide what to turn on. Nothing outside `~/.ironpet` is changed until you confirm the welcome window on first launch.

## Reporting a vulnerability

Please use GitHub's **Report a vulnerability** button on the repository's Security tab instead of a public issue. You'll get a reply within a week.

## What runs where

- **Local HTTP server.** The app listens on `127.0.0.1` only (port written to `~/.ironpet/port`). Every request has to carry the random 256-bit token in `~/.ironpet/token` (mode `0600`), or it gets a 403. The `/test/*` endpoints exist only when the app is started with `--test-mode`.
- **Hooks.** `~/.ironpet/bin/ironpet-hook` is called by the agents you choose to watch (Cursor, Claude Code, Codex, Gemini CLI, GitHub Copilot and Pi), so ironpet can show sessions you started yourself. The welcome window and Settings list only agents found on this Mac, and each is off until you turn it on. Hooks only report status: short timeouts, always exit 0, never block or fail your agents. They no longer approve anything. A chat that ironpet runs sets `IRONPET_ACP_RUN=1` on the agent, and the hook script skips those runs.
- **Agents over ACP.** Chat talks to the agent over the [Agent Client Protocol](https://agentclientprotocol.com) (JSON-RPC on the agent's stdin and stdout). ironpet starts the agent you pick from your own install, found through your login shell's `PATH`: `cursor-agent acp`, `gemini --acp`, `opencode acp` and so on. Claude Code, Codex and Pi have no ACP mode of their own, so ironpet runs a small adapter (a single `.mjs` file in `IronPet.app/Contents/Resources/acp/`) on your Node 22 or newer. The adapter drives your installed `claude`, `codex` or `pi`, which ironpet passes in `CLAUDE_CODE_EXECUTABLE`, `CODEX_PATH` or `PI_ACP_PI_COMMAND`. The app bundle contains no agent and no JavaScript runtime. ironpet declares no `fs` or `terminal` client capability, so agents read and write files and run commands with their own tools, under their own permission settings. It lists an agent in the picker only when its command exists and, for agents with native ACP, answers `initialize` (ironpet starts each one briefly to check).
- **Approvals.** The agent decides when to ask. When it wants to run a tool it may send `session/request_permission`, and ironpet either answers or shows an Allow / Deny card. File edits, deletions and shell commands ask. Reads, searches, web fetches and read-only MCP tools (names starting with `get`, `list`, `search` and similar) are allowed without a card. The per-chat **Auto** switch skips the cards for that chat only. The agent stays in its normal asking mode and ironpet answers for it. Even with Auto on, commands that match a destructive pattern (`rm -rf`, `git push --force`, `git reset --hard`, `git clean -f`, `DROP TABLE`, `mkfs`, `dd if=`, …) still ask. Auto resets with each new chat and when you open a chat from history. It is remembered only for the chat that was open when the app quit, so a restart doesn't silently turn it off mid-task. Edits of ironpet's own memory notes (`~/.ironpet/memory`) don't ask; deleting or moving a note file, and any change under `memory/.history`, which Undo and forgotten notes come back from, still asks (or runs under Auto). Paths are compared without case, and every path a call names counts, a move's destination included. ironpet's own task tools on its `ironpet` MCP server don't ask either (`tasks_list`, `tasks_get`, `tasks_create`, `tasks_update`, `tasks_close`, `tasks_suggestions_list`, `tasks_suggestion_accept`, `tasks_suggestion_reject`); `tasks_delete` asks. The memory tools on that server (`memory_remember`, `memory_forget`, `memory_search`, `memory_get`) don't ask either: they only write one-line notes in `~/.ironpet/memory`, and `memory_forget` moves a note to `.history` instead of deleting it, so nothing is lost. They skip the card only when the agent names the `ironpet` server (`mcp__ironpet__<tool>`), as the `status_*` tools do: names this plain could be another server's, so the same name on another server, or reported bare, still asks. A request that ironpet cannot show (the app quit, or the turn was stopped) is answered with a cancel, and an unanswered card waits until you decide or stop the turn.
- **Questions.** An agent can ask you a form through `elicitation/create` (Claude Code's AskUserQuestion, and form requests from its MCP servers). The answers you submit go to that agent and are saved in the chat's thread file in `~/.ironpet/threads`, like the rest of the transcript. A form ironpet cannot draw is declined, and stopping the turn or closing the chat answers an open form with a cancel. ironpet does not advertise URL elicitation.
- **Approval cards depend on the agent.** ironpet cannot force an agent to send `session/request_permission`. An agent that runs a tool without asking, because of its own settings, an allow-list or a "never ask" mode, does so without any card, and ironpet only sees the tool call afterwards. For example, `cursor-agent acp` runs commands on its own allow-list (such as `ls`) without asking and asks for the rest, and with `"approvalMode": "unrestricted"` in `~/.cursor/cli-config.json` (Run Everything) it asks for nothing at all. Check an agent's own permission settings before you rely on the cards in the chat. Task runs check them for you (see Task runs below). The destructive-command check applies only to requests the agent sends.
- **One download, only when you allow it.** If you pick Claude Code, Codex or Pi and your PATH has no Node 22 or newer, the chat shows a **Download Bun** button instead of failing. Only a click starts the download. ironpet fetches Bun 1.4.4 (about 40 MB) from `github.com/oven-sh/bun`, reads the expected SHA-256 from the same release's `SHASUMS256.txt`, and unpacks the archive only if the checksum matches. It then clears the macOS quarantine flag on that file and keeps it at `~/.ironpet/runtime/bun`. A mismatch or a failed download shows an error and runs nothing. This is the only network request ironpet makes on its own initiative besides the optional GitHub, Sentry and voice features below.
- **Telegram (off by default).** With Chat from Telegram on, ironpet long-polls `api.telegram.org` for the bot whose token you saved in Settings → Integrations, and sends each answer to a Telegram-started message back through the same API, so that text passes through Telegram's servers. Only Telegram user ids in `telegram.allowedUsers` reach the chat; everyone else is ignored. With nobody allowed, a `/start` shows an Allow / Deny bubble on the Mac, and only the first user can be paired that way. An allowed user can start turns in the chat that is open on the Mac, so treat their account like your own. A turn started from Telegram follows the same approval rules as one typed on the Mac. With Auto on, an allowed Telegram user can run non-destructive commands, file edits and MCP tools without anyone approving them, so keep `telegram.allowedUsers` short. Destructive commands still ask, and the card goes to Telegram as Approve / Reject buttons as well as to the Mac. With Auto off, edits, deletions and shell commands ask as usual. Reads, searches and read-only tools run without a card. Files an allowed user sends are saved under `~/.ironpet/telegram/files/` (up to 20 MB each) and handed to the agent, and voice messages go to the transcription server from Settings → Voice. An allowed user can also approve or reject tool approvals of a turn they started, from Telegram. The token is in the Keychain item `ironpet.telegram`, never in `~/.ironpet`.
- **Tasks.** The chat agent and any program that can read `~/.ironpet/token` (the `IronPet tasks` CLI) can create, change and delete tasks through the local server. Tasks are data in `ironpet.db` and never run anything, so the tools need no approval card, like memory-note edits. An automation `prompt` action runs in your chat with the chat's full tools, so it can change tasks and files like anything you type there. An agent that creates or changes one needs your Approve first. A prompt that uses poll item data (`{{item.*}}`) never goes to the chat, because that text comes from outside. It runs in a background agent that gets no MCP tools and cannot change tasks, like the one for meeting summaries. Meeting action items come from what people said on a call, so they are only suggestions until you press Add in the Tasks section or a chat agent accepts them with `tasks_suggestion_accept`, and they are never sent to an agent as instructions. The same goes for a watcher automation's `suggest_task` action: text from an email, a chat message or an issue only becomes a suggestion, with control characters removed, length limits, at most 10 per run and only an http or https link, and it becomes a task only when you press Add. The agent is told that task text is data.
- **Background jobs.** A chat agent can start a job (`jobs_start`), which runs your chosen agent unattended in a folder ironpet already knows (the front Cursor window, the chat's folder, folders open in Cursor, folders of watched agent sessions, recent chat folders, or `~/.ironpet/scratch`); a path the agent makes up is refused. In a chat without **Auto**, starting, adding to and stopping a job asks first. The job's own permission requests are answered as if Auto were on: commands and file edits run without a card, destructive commands (`rm -rf`, `git push --force`, `git reset --hard`, dropping tables and similar) wait for a click on Allow in a bubble. Only a click approves, never a chat or spoken answer. The Auto caveats above apply: a command that is harmful but not on the destructive list runs, and an agent that runs tools without asking does so with no card. The MCP connection a job gets (`/mcp/job`) does not offer the tools that start, steer, stop or open jobs, so the job's agent is not invited to start more. That is not a hard boundary: the job runs commands as you, and like the task tools, anything that can read `~/.ironpet/token` can reach the full `/mcp`. Its transcript is saved in `~/.ironpet/threads` and its prompt, folder and last step in `ironpet.db` for 30 days.
- **Assistant tools.** `status_*` tools let chat agents read the sessions ironpet watches (prompt snippets, summaries), open alerts, tasks, the brief and recap, and recent meeting summary lines with your open action items. They run without a card, like the task tools. What an agent reads through them goes to that agent's provider.
- **Memory.** Ghost's notes are plain Markdown in `~/.ironpet/memory/` (`me.md`, `people.md`, `projects/*.md`), with earlier versions in `memory/.history/`. ironpet's own writes (the learning pass, the memory tools, the Settings editor, Undo) copy the old file to `.history` first; a chat or job agent may also edit a note file with its own file tools without a card, and that edit gets no `.history` copy, no secret check and no Undo (deleting or moving a note file, or changing `.history`, asks). The restricted run for automation prompts with `{{item.*}}` text may not edit them at all. Through the memory tools, a note an agent proposes is one line of at most 240 characters, and one that holds anything ironpet's secret patterns would redact (keys, tokens, passwords, card numbers) is dropped, not saved. The chat agent reads up to about 12 KB of notes at the start of each thread, and can save, forget and search them with the `memory_*` tools (see Approvals). Any chat agent can read, through `memory_search` and `memory_get` and without a card, your past chats with any agent (your messages and the replies, not tool output), meeting summaries and transcripts, the notes, their earlier versions when it asks for them, and your screen captures when screen capture is on; what it reads goes to that agent's provider. An automation that runs in its own session (`session` `new` or `own`) has the same tools, but ironpet knows it is not your chat: its notes are marked with the automation, may not go into `me.md`, need an explicit project, and it may not forget notes. That session does not get the memory folder as an extra folder, and ironpet refuses its edits, deletes and moves of memory files. A shell command it runs could still write there, as it could write any of your files. A background job's session has the same memory tools as your chat, since it works on what you asked for: its notes are marked with the job (`job:<id>`) and go to the job's folder's project unless it names another, and it may forget notes. It starts with the same notes as a new chat. Its transcript is searchable like a chat's, but the reflection pass does not read it, because its first message is the chat agent's instructions, not yours. `.history` keeps the newest 50 versions of each file. Notes and search results are facts recorded earlier and data, never instructions; the preamble and the tool descriptions say so, but a note or a past message that tries to steer an agent can still skew what it does. Settings → Memory lists the last 20 changes with Undo and has **Forget Everything**, which deletes the files, `.history` and their index.
- **Memory reflection (on by default).** When a chat has been quiet for 30 minutes (`memory.quietMinutes`), or you start a new chat or open another thread, ironpet sends the new user and assistant messages of that thread (no tool output, at most 24,000 characters) and, for a chat, your notes, no more of them than a new chat's preamble holds (about 4 KB about you, 6 KB of the project and 2 KB of people); a meeting summary or an automation answer is sent without your notes, since its agent never got a preamble, to the agent that already had that text: by default the chat's own agent, the meeting summary agent for a summary (`summary.md`, never the audio or the transcript), and the agent that ran an automation for its final answer (in your chat or in the automation's own session). Claude Code runs the pass on `haiku`; other agents on their default model. With an agent picked in Settings → Memory (`memory.reflectAgent`), only text that went to that agent is read, with `memory.reflectModel`, and the rest is skipped. Either way no provider gets text it did not already have (the check is by agent: an agent that can run models from several providers uses the cheap or picked model for the pass); the text is sent to it again, though, and the pass spends its quota. The restricted run for prompts with item text from outside (`{{item.*}}`) is never read, and neither are automation prompts. That agent runs restricted, like meeting summaries: in `~/.ironpet/scratch/memory`, with no MCP servers and no memory or screenshot folders, and ironpet refuses every permission request from it, so it cannot change files or run commands. It answers with JSON and ironpet writes the notes. Meeting summaries and automation answers carry text other people wrote, so notes from them may only describe people: never `me.md` or a project file (they have no project)md`, and may not replace existing notes; no pass replaces more than 5 notes in all. Undo of a Settings edit or a tidy goes back to the whole earlier file, so it is refused while a newer change to that file is in place. Tidying is off by default (`memory.tidy`): with it on, a file over its size limit goes whole to the same agent, including notes from chats with other agents and lines you wrote, and ironpet keeps the answer only if it is smaller, keeps at least a third of the notes and every note keeps its date and source. In `--test-mode` a pass runs only when an e2e scenario asks for one. Turn it off under Settings → Memory → Learn from chats (`memory.reflect`); messages from while it was off, or from chats with an agent other than the picked one, are marked as read and never sent later. Each pass is recorded as Memory in the Usage tab.
- **Stream automations.** A `stream` trigger keeps a shell command running as your user, with your login-shell `PATH`, for as long as the automation is on. An agent that creates or changes one needs your Approve before the command first starts, and again after every change to the command. Rejecting turns it off. ironpet starts the command in its own process group and stops the whole group when you pause, delete or change the automation or quit the app (SIGTERM, then SIGKILL after 2 seconds). Each output line is data from outside: it only fills `{{item.*}}`, which is quoted for the shell in a `shell` action, and a `prompt` that uses it runs in the restricted background session, as for polls. Lines over 64 KiB and more than 20 events a second are dropped, so a noisy command cannot flood the action. The command may not hold a literal token.
- **Morning brief and recap.** A `digest` action reads only what is already on the Mac (tasks, alerts, the activity log in `ironpet.db`, the sessions in memory and meeting summaries under `~/.ironpet/meetings`), runs no command and starts no agent, so it needs no approval, whoever created it. It writes only the run in the automation history and, for its schedule, the last slot it delivered in `automation_daily` in `ironpet.db`. The bubble and the Today page show task titles, alert titles and meeting action items beside Ghost, as the other bubbles do.
- **No API keys.** Chat goes through the sign-in your agent already has. If an agent says it needs you to sign in, ironpet shows a button: for an agent that signs in over ACP it calls `authenticate`, and for a terminal sign-in it opens Terminal with the command the agent gave. ironpet sends nothing anywhere itself, except the optional GitHub and Sentry polling below, voice notes, spoken replies and voice mode if you turn them on, and the Bun download above.

## What ironpet reads

- `~/.config/gh/hosts.yml` and the `gh` CLI, only with GitHub alerts on (off by default).
- `~/.ironpet/sentry.json` and its Keychain token, only after you've configured Sentry.
- Cursor's `storage.json` and iTerm2 via AppleScript, to find the project you're working in.
- The microphone, only while you record a voice note with voice notes on (off by default). macOS asks for permission the first time you record, not before.
- The microphone and one app's audio (or all system audio, through ScreenCaptureKit), only while a meeting transcript is recording, with meeting transcripts on (off by default). macOS asks for microphone and Screen & System Audio Recording access the first time you start one.
- With the welcome back summary on (`welcomeBack.enabled`, on by default): the system idle time and screen-lock state every 2 s, wake-from-sleep notifications, and, once you have been idle past `reminders.idleResetMinutes` (or right after the Mac wakes), which apps are capturing microphone input (Core Audio's process list: bundle id and pid, no audio and no permission prompt). This decides whether you are away or on a call; nothing is stored or sent.
- Wispr Flow's local database, to pick up dictation while the chat is open.
- The general pasteboard, briefly, after you select text in a chat message and release the mouse. ironpet sends the same copy command as Cmd-C to read the selection for the "Ask about this" button, then puts your earlier pasteboard contents back. It never reads the pasteboard otherwise, and the selected text stays in the chat unless you send it.

| Path | Contents |
| --- | --- |

| `threads/` | Saved chats (agent, ACP session id, folder and the visible transcript) |
| `runtime/` | Bun, only if you allowed the download |
| `memory/` | Markdown notes Ghost keeps about you (`me.md`), the people you work with (`people.md`) and your projects (`projects/`), each note with the day and where it came from (a chat, a meeting folder name or an automation id). `.history/` holds every earlier version of each file. You can edit them; Settings → Memory → Forget Everything deletes them |
| `screenshots/` | Screen captures you attached to chats, and `attachments/` with files you attached. A draft over 64 KB is handled the same way |
| `HEARTBEAT.md` | The checklist the Heartbeat automation works through. ironpet writes the default entries once when the file is missing and never changes it afterwards. You and the chat agent edit it |
| `scratch/` | Working folder for chats that aren't about a project. `scratch/memory/` is the empty working folder of the memory reflection pass |
| `meetings/` | One folder per meeting transcript: the recorded audio as WAV chunks, `transcript.md`, `summary.md`. Kept until you delete them |
| `ironpet.db` | Automation state and logs, usage numbers, background jobs (title, prompt, folder, last step and result, kept 30 days after they end), and your tasks: titles, notes, links, history, suggestions from meetings and watchers, and where each task or suggestion came from (`source_ref`). The `capture_*` tables hold the redacted text of the windows you used while screen capture was on (see below). The `memory_*` tables hold a search index over your chat messages (yours and Ghost's, not tool output), meeting summaries and transcripts, your memory notes and their earlier versions; where the reflection pass stopped in each thread; and the log of note changes behind Recently learned. Forget Everything clears the notes' part and the log. The chat and meeting part follows the threads and meetings on disk: a meeting moved to the Trash leaves the index at once, and at each launch documents of threads and meetings that are gone are dropped. Done tasks are deleted after `tasks.keepDoneDays` (30 by default). The notifications (`notification_items`, `notification_links`) keep every bubble ironpet showed for 90 days: title, summary, the full description (up to 64 KiB, such as a whole background prompt reply or a script's report) and links, which are references (URLs, file paths, thread, session, task and alert ids) and never copies. Agents can read them through the `notifications_list` and `notifications_get` tools and `IronPet notifications`, which only read, over the same token-protected loopback server as the other tools. The activity log (`activity_events`) keeps what ironpet announced for 30 days: for agent sessions that needed you, failed or finished, the folder, agent, owner app and iTerm session, plus the agent's one-line summary or the request it is waiting on (up to 140 characters; never your prompt); automation bubble titles and bodies (up to 200 characters) and links; alert titles, subtitles and links; due and suggested task titles; meeting summary folders; and a finished or failed line for chats that ended while hidden (no chat content). It is recorded whether or not the welcome back summary is on, read only on this Mac, and never sent anywhere |
| `token`, `port` | Local server credentials |

The chat that was open when the app quit is reopened on launch. Its id, its Auto switch, your unsent draft and the paths of attached screenshots are kept in the app's preferences (`dev.ironpet.app`), which `uninstall.sh` deletes.

Delete the folder to erase all of it, or run `./scripts/uninstall.sh` to remove ironpet completely (hooks, login item, app, Keychain item, and optionally this folder).

## Screen capture reads other apps and stores their text

Screen capture is off by default. Turning it on in Settings asks macOS for Accessibility access. Screen Recording is asked for only when you also turn on the screenshot fallback.

- **What is read.** The text of the focused window through Accessibility: static text, headings, text areas and text fields, as a tree. Buttons, menus and similar controls are read for their name only. Hidden elements are skipped. Secure text fields are never read: the source reads their role and nothing else, so their value never enters ironpet's memory. Password managers and other denylisted apps, private browser windows, non-web URLs and the locked screen are skipped in Swift code that no setting can override. Private-window detection looks at window titles, so a window with an unusual title can slip through. Keyboard, scroll and click events are used as timing only, to decide when to capture. No key or pointer position is read.
- **Screenshot fallback.** Off by default. When a window has no readable text, ironpet takes a screenshot of exactly the window it read (matched by its window id, never another window of the app) with ScreenCaptureKit and reads it with Apple Vision. The image stays in memory and is never written to a file.
- **Redaction.** Before anything is stored, rules replace secrets in the text with `[redacted:<kind>]`: provider keys and tokens (AWS, GitHub, GitLab, Anthropic and other `sk-` keys, Stripe, Slack, Google, npm, SendGrid), JWTs, private key blocks, `user:password@` in URLs and secret URL parameters, `password=`, `token:` and `.env`-style assignments, card and bank numbers, and long random strings. These rules are patterns, so a secret in a form they do not know passes through them. The unredacted text is never stored. An optional on-device privacy filter can plug into the write and read paths (`CapturePrivacyFilter`). None ships yet.
- **Where it is stored.** In the `capture_window`, `capture`, `capture_fts`, `capture_node`, `capture_block_seen` and `capture_draft` tables of `~/.ironpet/ironpet.db`, with the file and its WAL files set to mode `0600`. The text is redacted and not encrypted. The database runs with `secure_delete` on, so freed pages are zeroed. A prune and Delete all captures also empty the write-ahead log with a checkpoint, which is best effort (it does nothing while a reader holds the log). The disk itself may keep older blocks, so "deleted" means removed from the database and its log, not wiped from the disk. Captures, block records, drafts and tree nodes no remaining capture uses are deleted after the retention setting (30 days by default). Captures stored by earlier versions are deleted on upgrade. Text you typed into a field is kept as a draft until it is sent or discarded, redacted like the rest.
- **Who can read it.** The agents you run in ironpet's chat, through the `screen_search` and `screen_window` MCP tools, over the same loopback server and token as the other tools. They return stored, redacted text. Whatever an agent reads goes to that agent's provider. ironpet itself sends nothing anywhere. The captured text includes what other people wrote, such as Slack messages, so tool descriptions and the `ironpet-tasks` skill tell agents to treat it as data, never as instructions. A message that tries to steer an agent can still skew what it does. The `screen_*` tools only read, so like the `tasks_*` tools they run without an approval card. An agent that also has shell or automation tools could act on injected text, so the worst case is not limited to a wrong task or update. Closing a task on screen evidence alone needs your confirmation, per the skill.

## Desktop control lets agents operate other apps

Desktop control is off by default (`desktopControl.enabled`, Settings → Screen). Turning it on asks macOS for Accessibility access if ironpet lacks it. The agents you run in ironpet then get the `desktop_*` MCP tools, over the same loopback server and token as the other tools.

- **What an agent can do.** Read any window's accessibility tree live (text, names and values, redacted like screen capture), press buttons, set or insert text, pick options, set checkboxes and expand rows, focus elements and raise windows, through Accessibility actions. Two tools go beyond that: `desktop_key` and `desktop_open_url`, described below. ironpet sends no mouse events. `desktop_screenshot` returns one window's picture when Screen Recording is allowed. The picture stays in memory.
- **What it cannot do, in Swift code no setting overrides.** Read or act on password fields (role only), password managers and the other denied apps, apps you excluded from screen capture, private browser windows, denied or non-web browser addresses, or ironpet's own windows. Nothing works while capture is paused or the screen is locked. Private-window detection looks at window titles, so a window with an unusual title can slip through.
- **Approval.** An action on an element or window whose text says send, pay, delete, submit or buy (generic verbs, not app names) waits for Approve in a bubble. A rejection or two minutes of silence fails it. The element is checked again after the answer. The check reads text, so a control with an icon and no name, or a label in another language, does not trigger it. Treat Auto mode accordingly, because Auto skips the chat's card for MCP tools.
- **Key events.** `desktop_key` posts a key down and key up to one app's process with `CGEvent.postToPid`. It never posts to the system-wide event stream, so a key reaches that app and no other. It goes to whatever element has the keyboard focus in that app, and the app is raised first when it is not in front. The same app, window and address rules as the other tools apply, and a key is refused while a password field has the focus. Cmd+Return, Cmd+Q and Cmd+W always wait for Approve. Return or any Cmd combo also waits when the focused window title or element text says send, pay, delete, submit or buy. Letters, Tab, Escape and the arrows never ask, so an agent can type text one letter at a time into a field that is not a password field, and into a control whose name carries no trigger word. The focus is read again after your answer, and a key that now needs approval but was not asked about is refused. The log keeps the key name (for example `key cmd+l`) and the focused element's role and name, which means keys typed one by one appear in it.
- **Opening addresses.** `desktop_open_url` opens an `http` or `https` address in a new tab of the browser the agent names, else the frontmost browser, else the default one. Other schemes (`file`, `javascript`, `data`, browser-internal pages, `mailto` and so on) and addresses with a user name or password are refused, and so are hosts on the screen capture deny list (the password manager sites). Opening a page can still send data: an agent can put anything it has read into the query string, and the page loads in your logged-in browser. It does not look at the browser window, so with a private window in front the page may open there. The log keeps the address with secret query parameters removed.
- **Prompt injection.** Everything on screen is written by other people and apps, and the tools tell agents to treat it as data. A page that steers an agent can still make it press something that has no trigger word. The approval gate and the log are the limits, not a guarantee.
- **What is kept.** Every action is stored in the activity log (`activity_events`, kind `desktop.action`) for 30 days: time, app name, window title (up to 80 characters), element role and name (up to 80), the action, its outcome and a short note. Values you or an agent typed are not kept. The log stays on this Mac. Whatever an agent reads goes to that agent's provider.

## Voice notes send audio to a server you choose

With voice notes on (Settings → Voice, off by default), each recording is uploaded as a WAV file to the base URL you set, along with the model name and, if you saved one, an `Authorization: Bearer` header carrying your API key. That may be a service such as OpenAI or Groq, or a server on your own Mac. ironpet does not choose the server or fall back to another. While the feature is off, the microphone is never opened and nothing is sent, apart from the one-second test tone that the Test connection button uploads when you press it. The key lives in the Keychain item `ironpet.voice` and is never written to `~/.ironpet`. Recordings are held in memory only: the last one is kept until its transcription succeeds, so Retry can send it again, and none is written to disk. A plain `http://` base URL sends audio and the key unencrypted, so use it only for `localhost`.

**Spoken replies (off by default).** With Settings → Voice → Read replies aloud automatically on, the text of a chat reply is sent to the same base URL (`POST /audio/speech`, with the speech model, the voice and your API key) when the reply answers a message you sent from the chat (not from Telegram or an automation). With it off, reply text is sent only when you press a reply's speaker button or choose Read Aloud, and only for that reply. The button works with the switch off. Only the reply's prose is sent: code blocks, tables, bare links and emoji are left out, and so is anything after the first minute or so. The audio that comes back is played and kept in memory only. With the feature on, Settings also asks the server for its voice list (`GET /audio/voices`) while the Voice page is open; with it off, opening the page sends nothing. Preview sends one fixed line, and only when you press it or turn the switch on. While spoken replies are on, ironpet checks every 2 s which apps are capturing microphone input (bundle id and pid, no audio and no permission prompt), so a reply is not read aloud over a call; nothing is stored or sent. With the feature off, no text is sent and nothing is checked. With a remote server, reply text leaves your Mac.

## Voice mode listens and acts on what you say

With voice mode on (Settings → Voice → Conversation, off by default), the voice-mode shortcut opens a conversation. Turning the switch on uploads the one-second test tone and speaks one fixed line, to check the server.

- **The microphone is open only during a conversation.** It opens when you press the shortcut and closes when the conversation ends: on goodbye, Esc, the shortcut, the set silence (20 s by default) or a call starting. Each utterance is cut out of the stream on this Mac (an energy level, no model) and uploaded as a WAV to the transcription server, like a voice note. Audio, yours and the pet's replies, is held in memory only and never written to disk. Only utterances are sent, each with about a second of the sound around it; the stretches in between are not.
- **What you say goes to the chat's agent.** The transcript is sent as a prompt to the chat's agent (and its model provider) in a session of its own, with your notes from `me.md` and `people.md` (those the message names) in its first turn. The reply's text goes to the speech server to be read aloud. The conversation is saved as a thread in `~/.ironpet/threads/`, and when it ends memory's reflection pass reads it like a chat you left (only when learning from chats is on).
- **The voice session can't run commands or edit your files.** Its permission requests are allowed only when the chat would allow them without Auto and without asking: reads, searches, fetching a URL, edits to ironpet's memory notes, read-only MCP tools, and ironpet's own tools (status, memory, projects, tasks, screen search, and starting, steering or stopping jobs). Everything else is refused with a note to use a background job. A background job started by voice runs under the same Auto rules as any job: destructive commands wait for Allow in a bubble, and nothing spoken answers that bubble.
- **"Cancel that".** A job started from voice, or a finished job a voice follow-up restarts, is held until the pet has said what it started and 5 s more (at most 60 s in all), so "cancel that" stops it before its agent runs. A follow-up to a job that is already running reaches it after its current turn, as from the chat.
- **Wispr Flow mode.** With Listen with set to Wispr Flow, ironpet opens no microphone of its own. While the pill is up, ironpet is the active app and reads Wispr's local history (`~/Library/Application Support/Wispr Flow/flow.sqlite`, read-only) for entries addressed to ironpet, as the chat already does.
- **Calls and presence.** While voice mode is on, ironpet checks every 2 s which apps are capturing microphone input (bundle id and pid, as for spoken replies). A conversation doesn't start, and ends, during a call or a meeting recording. Spoken job updates are skipped then, and while the Mac has been idle for the away time under Reminders.
- **Esc is taken globally while a conversation runs**, so it ends the conversation from any app. It's released when the conversation ends.

## Meeting transcripts record other people

With meeting transcripts on (Settings → Meetings, off by default), starting a meeting records two tracks until you stop: your microphone ("Me") and the audio of the app you picked, or all system audio ("Them"). ironpet's own sound is excluded. Both are written as 16 kHz mono WAV chunks to `~/.ironpet/meetings/<date-time>/` and stay there after the meeting. They are your recording, so ironpet never deletes them; remove the folder when you no longer need it. At most one chunk (up to 5 minutes per track) is held in memory at a time.

- **Audio goes to the configured server.** Every chunk is uploaded to the base URL under Settings → Voice, with the model name and your API key if you saved one. A plain `http://` URL sends it unencrypted, so use it only for `localhost`. Chunks that fail are retried against the same server.
- **The transcript goes to the chosen agent.** When a meeting ends and "Summarize automatically" is on, the full text of `transcript.md` is sent to the agent set as the summary agent (an ACP agent such as Claude Code or Cursor), and from there to that agent's model provider. Turn the setting off and no agent runs. Summaries and transcripts are also in Ghost's memory index, so any chat agent can read them later with `memory_search` and `memory_get` (see Memory above), and the summary, not the transcript, can go to the memory reflection agent when it is also the summary agent.
- **The summary agent cannot change anything.** It runs over ACP in the meeting folder only (ironpet's memory and screenshot folders are not shared), and ironpet answers every `session/request_permission` from it with a refusal, so it cannot edit files or run commands. ironpet itself writes `summary.md` from the agent's text answer. The agent can still read files inside the meeting folder.
- **Regenerate sends the same data again.** Regenerating a meeting sends its saved audio to the transcription server and the new transcript to the summary agent, the same two destinations as the meeting itself, and only when you press the button. It writes `transcript.prev.md`, `summary.prev.md` and short-lived `*.new.md` files inside the meeting folder.
- **Consent.** Recording people without their consent is illegal in many places (for example §201 StGB in Germany). The first meeting shows a notice, the picker repeats it, and the recording status shows in the pet's bubble. You can close that bubble, but the pet then shows a red Recording button for as long as ironpet records, and clicking it brings the bubble back.
- **Permissions are asked late.** Microphone and Screen & System Audio Recording access are requested when you press Start recording for the first time, never at launch and never with the feature off.
- **Voiceprints (off by default).** With "Recognise speakers in meetings" on, ironpet computes a voice embedding for each speaker of the Them track on this Mac. Nothing is sent anywhere for this. After you name a voice, a 256 number centroid, the name, seconds of speech and a meeting count are kept in `~/Library/Application Support/IronPet/voices.enc`, encrypted with AES-GCM under a key in the Keychain item `ironpet.voiceprints`. It is biometric data about people who have not consented, so tell them. Settings has **Forget this voice** and **Forget all voices**, which delete the entries from the file at once. The first time you turn it on, the models (about 21 MB) are downloaded from Hugging Face by FluidAudio.
- **Quitting.** Quitting ironpet during a meeting writes the audio captured so far and what is already transcribed. Chunks not yet transcribed are marked as such in `transcript.md`.
